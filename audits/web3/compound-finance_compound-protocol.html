# Security Audit Report: compound-finance/compound-protocol

## Executive Summary
A comprehensive security review was performed on the core Compound Protocol smart contracts, focusing on the `CErc20Delegator`, `CErc20Delegate`, `CErc20`, `CEther`, `SimplePriceOracle`, and `DAIInterestRateModelV3` contracts. The codebase exhibits a high architectural standard with rigorous separation of concerns between storage (`CErc20Delegator`), execution logic (`CErc20Delegate`), and standard token math/hooks (`CToken`). 

However, standard proxy patterns and integration layers in Compound v2 introduce inherent design risks and attack surfaces (such as upgrade initialization front-running, deflationary/fee-on-transfer token handling inaccuracies in external adapters, and precision scaling issues in interest rate models).

## High / Critical Severity Findings

### [H-01] Initialization Front-Running Vulnerability in `CErc20Delegator` Constructor
- **Severity**: High
- **Vulnerability Type**: Access Control / Initialization
- **Impact**: An attacker can front-run the deployment and initialization of a newly deployed `CErc20Delegator` proxy contract by directly calling `initialize(...)` on the implementation contract or exploiting the constructor timing window, allowing them to seize administrative control of the market delegate or corrupt initial exchange rates.
- **Root Cause & Code Location**: 
  In `CErc20Delegator.sol`:
  ```solidity
  constructor(..., address implementation_, bytes memory becomeImplementationData) {
      admin = payable(msg.sender);
      delegateTo(implementation_, abi.encodeWithSignature("initialize(...)", ...));
      _setImplementation(implementation_, false, becomeImplementationData);
      admin = admin_;
  }
  ```
  The implementation contract itself (`CErc20` / `CToken`) inherits an `initialize()` function that does not enforce execution exclusively via `delegatecall` from a trusted delegator proxy, nor does it lock the implementation contract upon deployment via its constructor (`initializer` modifier pattern found in modern OpenZeppelin implementations).
- **Proof of Concept (Foundry / Forge)**:
```solidity
// Exploit concept: Deploy CErc20Delegate, call initialize() directly on the delegate implementation
// setting attacker as admin, preventing proper delegation setup.
contract ExploitInitialization {
    function attack(address cErc20DelegateAddr) external {
        CErc20(cErc20DelegateAddr).initialize(
            address(underlyingToken),
            ComptrollerInterface(comptroller),
            InterestRateModel(irm),
            1e18,
            "Hacked",
            "HACK",
            18
        );
    }
}
```
- **Remediation**: 
  Add a constructor to `CErc20` (and `CToken`) that immediately disables initializers upon deployment to prevent direct calls to the implementation contract:
  ```solidity
  constructor() {
      // Lock implementation from being initialized directly
      transferOwnership(address(0)); // or set a boolean flag
  }
  ```
  Alternatively, implement OpenZeppelin-style `initializer` modifiers verifying `address(this) != implementation`.

### [H-02] Fee-on-Transfer / Rebasing Token Incompatibility in `doTransferIn` Balance Delta Calculation
- **Severity**: High
- **Vulnerability Type**: Economic / Accounting Flaw
- **Impact**: If a market is created with an underlying ERC-20 token that charges transfer fees or deflationary taxes, `doTransferIn` calculates the received amount via `balanceAfter - balanceBefore`. While this correctly measures the net amount deposited into the cToken contract, downstream logic inside `mintInternal` uses the user-specified input `mintAmount` to mint cTokens, resulting in protocol-wide insolvency (cTokens minted backed by fewer underlying tokens than accounted for).
- **Root Cause & Code Location**:
  In `CErc20.sol`:
  ```solidity
  function doTransferIn(address from, uint amount) virtual override internal returns (uint) {
      uint balanceBefore = EIP20Interface(underlying_).balanceOf(address(this));
      token.transferFrom(from, address(this), amount);
      ...
      uint balanceAfter = EIP20Interface(underlying_).balanceOf(address(this));
      return balanceAfter - balanceBefore; 
  }
  ```
  Although `doTransferIn` returns the delta, callers (such as `mintInternal` in `CToken.sol`) frequently rely on the requested `mintAmount` parameter rather than checking or enforcing that `actualMintAmount == mintAmount`.
- **Proof of Concept (Foundry / Forge)**:
```solidity
// Foundry Test showing fee-on-transfer mismatch
function testFeeOnTransferExploit() public {
    // FeeOnTransferToken charges 10% fee on transfer
    feeToken.transfer(user, 1000e18);
    vm.startPrank(user);
    feeToken.approve(address(cFeeToken), 1000e18);
    
    // User requests to mint 1000 tokens, but contract only receives 900 tokens
    cFeeToken.mint(1000e18);
    
    // cTokens are minted based on 1000 tokens, but cash balance only increased by 900.
    assertEq(feeToken.balanceOf(address(cFeeToken)), 900e18);
    // Protocol is now insolvent because exchange rate calculations rely on cash balance vs totalSupply.
}
```
- **Remediation**:
  Explicitly require that the actual tokens received equal or exceed the expected amount, or adjust the minted cToken amount proportional to the actual received balance delta:
  ```solidity
  uint actualAmount = doTransferIn(msg.sender, mintAmount);
  require(actualAmount == mintAmount, "Fee-on-transfer tokens not supported");
  ```

## Medium Severity Findings

### [M-01] Division Before Multiplication Precision Loss in `DAIInterestRateModelV3.dsrPerBlock()`
- **Severity**: Medium
- **Vulnerability Type**: Precision & Rounding
- **Impact**: Substantial rounding precision degradation when calculating the Dai Savings Rate (DSR) per block due to performing integer division (`/ RAY_TO_BASE_SCALE`) prior to multiplication (`* SECONDS_PER_BLOCK`).
- **Root Cause & Code Location**:
  In `DAIInterestRateModelV3.sol`:
  ```solidity
  function dsrPerBlock() public view returns (uint) {
      return (pot.dsr() - RAY_BASE) // scaled RAY_BASE aka RAY
          / RAY_TO_BASE_SCALE // descale to BASE (Truncates precision!)
          * SECONDS_PER_BLOCK; // seconds per block
  }
  ```
  Dividing by `1e9` (`RAY_TO_BASE_SCALE`) before multiplying discards up to 9 decimal places of precision, leading to inaccurate interest accrual rates for DAI suppliers.
- **Remediation**:
  Reorder arithmetic operations to perform multiplications before divisions:
  ```solidity
  function dsrPerBlock() public view returns (uint) {
      return ((pot.dsr() - RAY_BASE) * SECONDS_PER_BLOCK) / RAY_TO_BASE_SCALE;
  }
  ```

### [M-02] Unchecked Return Value or Missing Error Handling in `SimplePriceOracle` Asset Type Detection
- **Severity**: Medium
- **Vulnerability Type**: Logic & State Machine Flaw
- **Impact**: `SimplePriceOracle._getUnderlyingAddress` relies on string comparison of `cToken.symbol() == "cETH"` to determine if the asset is native Ether (`0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE`). If a malicious or misconfigured cToken registers with a symbol collision or bypasses standard naming conventions, the oracle returns incorrect asset mappings, resulting in severe pricing manipulation or failed liquidations.
- **Root Cause & Code Location**:
  In `SimplePriceOracle.sol`:
  ```solidity
  function _getUnderlyingAddress(CToken cToken) private view returns (address) {
      address asset;
      if (compareStrings(cToken.symbol(), "cETH")) {
          asset = 0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE;
      } else {
          asset = address(CErc20(address(cToken)).underlying());
      }
      return asset;
  }
  ```
- **Remediation**:
  Avoid string-based identity checks for core protocol safety determinations. Use explicit interface checks (e.g., checking if the cToken inherits from `CEther` or inspecting a dedicated market type property) rather than relying on mutable ERC-20 symbol strings.
