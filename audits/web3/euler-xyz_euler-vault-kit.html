# Security Audit Report: **euler-xyz/euler-vault-kit**

> **Scope** – The audit covers the Solidity source files shipped in the repository, namely the dummy ERC‑20/EToken helpers, the **IRMLinearKink** interest‑rate model, and the **BeaconProxy** generic factory proxy. No external contracts (e.g., the actual vault implementation) were available, so the analysis is limited to the code that is present.

## High / Critical Severity Findings

### [C‑01] **BeaconProxy Allows Unchecked Implementation & Unrestricted Calldata Tail Injection**

| Category | Detail |
|----------|--------|
| **Severity** | Critical |
| **Vulnerability Type** | Proxy mis‑configuration → arbitrary delegatecall target & calldata manipulation → re‑entrancy / storage‑corruption |
| **Impact** | An attacker who can control the **beacon** (the contract that the proxy queries for the implementation address) can point the proxy to any contract, including a malicious one that steals assets, re‑enters the proxy, or corrupts the proxy’s storage. Even when the beacon is trusted, the proxy **always appends up to 128 bytes of “metadata”** to the calldata before delegating. If the implementation reads calldata bytes directly (e.g., via `abi.decode`, assembly `calldataload`, or `bytes calldata` arguments), the attacker can influence those extra bytes at deployment time, potentially causing **function selector collisions** or **parameter tampering**. Because the proxy has **no re‑entrancy guard** and no storage layout validation, a malicious implementation can call back into the proxy (or any other contract) before the original call finishes, leading to classic re‑entrancy attacks on the vault that uses this proxy. |
| **Root Cause & Code Location** | `BeaconProxy` – `fallback()` (lines 55‑84). The proxy: <br>1. **Staticcalls** the beacon for the implementation address without any validation (`staticcall(gas(), beacon_, 0, 4, 0, 32)`). <br>2. **Appends** the immutable `metadata0‑3` directly after the original calldata (`mstore(calldatasize(), metadata0_) …`). <br>3. Performs a **delegatecall** to the returned implementation with the *augmented* calldata. No checks on the returned address, no length verification, and no protection against re‑entrancy. |
| **Proof‑of‑Concept (Foundry / Forge)** | The following test demonstrates that a malicious beacon can force the proxy to delegate to an attacker‑controlled contract that drains ERC‑20 tokens from the proxy’s storage. The test also shows that the injected metadata can be used to alter a function argument. |
