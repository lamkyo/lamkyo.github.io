# Security Audit Report: Uniswap/v4-core

## Executive Summary

**Contracts analyzed:** `PoolManager`, `ProtocolFees`, `ERC6909`/`ERC6909Claims`, `Extsload`, `Exttload`, `NoDelegateCall`, and libraries `Pool`, `SwapMath`, `FullMath`, `TickBitmap`, `Lock`, `CurrencyReserves`.

**Overall posture:** Strong. This codebase has been through multiple professional audits and formal verification. The flash-accounting model (transient-storage deltas + `NonzeroDeltaCount` invariant enforced at `unlock()` exit) is a sound replacement for reentrancy guards, and `noDelegateCall` correctly blocks proxy-bypass of the lock. No Critical or High severity fund-loss vulnerabilities were identified in the provided source. The findings below are Medium/Low severity, mostly **known and documented design trade-offs**, but they are actionable for integrators and hook developers.

**Risk level:** LOW (with integrator-facing caveats).

---

## High / Critical Severity Findings

None identified. Specifically checked and cleared:

- **Reentrancy:** All state-mutating pool functions are gated by `onlyWhenUnlocked`, which requires the caller to be inside `unlockCallback`. The `NonzeroDeltaCount != 0` check at the end of `unlock()` guarantees solvency — no party can exit the callback owing the manager a nonzero delta. External calls to hooks occur *before* `_accountPoolBalanceDelta`, but deltas are transient-accounted, so no invariant is violated mid-call.
- **Access control:** `setProtocolFee`/`collectProtocolFees` are controller-gated; `updateDynamicLPFee` correctly restricts to the pool's own hook address and requires the dynamic-fee flag; `Owned` is initialized in the constructor (no uninitialized-proxy risk).
- **Precision:** `SwapMath.computeSwapStep` rounds fees up and amounts out down consistently; `FullMath.mulDiv` handles phantom overflow; protocol fee rounds down favoring LPs (documented).

## Medium Severity Findings

### [M-01] `feeGrowthGlobal` inflation via self-donation enables fee theft from passive LPs
- **Severity:** Medium (High in adversarial pool compositions)
- **Vulnerability Type:** Economic / Logic
- **Impact:** An attacker who is also an LP can atomically `donate` and `modifyLiquidity(-delta)` within one `unlockCallback` to inflate `feeGrowthGlobal`, harvesting fees owed by *other* LPs in the same range. This is explicitly acknowledged in the `Pool.State` NatSpec, but it remains a real griefing/theft vector for pools with mixed passive liquidity.
- **Root Cause & Code Location:** `Pool.donate()` — any unlocked caller can add arbitrary `feeGrowthGlobal0/1X128` with no per-position accounting constraint.
- **Proof of Concept:**
```solidity
contract DonateInflateTest is Test {
    // attacker + victim LP in same range [minTick, maxTick]
    // 1. unlock()
    // 2. donate(poolKey, hugeAmount0, 0)      -> feeGrowthGlobal0 inflates
    // 3. modifyLiquidity(-attackerLiquidity)  -> attacker collects inflated feesOwed0
    //    victim's later burn collects proportionally less (fee pool is fixed)
    // 4. settle attacker's net (donation minus stolen fees)
}
```
- **Remediation:** None available at the core level without breaking the donation feature (this is a documented trade-off). Mitigate at the periphery: routers/position managers should not treat `feeGrowthGlobal` as trustworthy for pricing LP claims, and hooks can gate `donate` via `beforeDonate`.

### [M-02] `sync()` is permissionless and can force native-currency settlement misaccounting / DoS on naive integrators
- **Severity:** Medium
- **Vulnerability Type:** State manipulation / DoS
- **Impact:** `sync` is callable by anyone at any time (not `onlyWhenUnlocked`). A malicious contract can call `sync(ERC20)` inside its own `unlockCallback` *between* a victim router's `sync` and `settle`, or call `sync` with a fresh balance snapshot so that a concurrent `settle` by another party attributes *that party's* deposit to the attacker's delta. Additionally, for native currency, an attacker calling `sync(currency0)` (address zero reset) mid-flight forces `_settle` to read `msg.value` only, causing under-crediting for integrators that pre-funded ETH — the code comments acknowledge this ("integrators should still call `sync` first to avoid DoS").
- **Root Cause & Code Location:** `PoolManager.sync()` and `_settle()` — transient `CURRENCY_SLOT` is global (not per-caller), so concurrent settlers in the same callback interfere.
- **Remediation:** Integrators must always pair `sync(currency)` → transfer → `settle()` atomically with no external calls in between, and never rely on pre-transferred ERC20 balances being credited without a fresh `sync`. A core-level fix (per-caller synced currency keyed on `msg.sender`) would change gas profiles; document as invariant for router authors.

### [M-03] Unbounded loop in `extsload(bytes32, uint256 nSlots)` — gas griefing / OOG
- **Severity:** Medium (Low direct impact, view-only)
- **Vulnerability Type:** Resource exhaustion
- **Impact:** `nSlots` is unvalidated; a caller (or an on-chain aggregator invoking it) with a huge `nSlots` will allocate unbounded memory and revert with OOG. Because it's a `view` function this cannot corrupt state, but it can brick off-chain/contract readers that pass user-controlled `nSlots`, and `mload(0x40)`-based allocation can collide with the `"memory-safe"` annotation assumptions if the free-memory pointer isn't updated (it isn't — `0x40` is never advanced, so subsequent Solidity memory ops in the same call frame would overwrite the returned buffer; harmless here as the function returns immediately, but fragile if copied).
- **Root Cause & Code Location:** `Extsload.extsload(bytes32,uint256)` — no upper bound on `nSlots`.
- **Remediation:** `require(nSlots <= MAX_SLOTS)` (e.g. 1000) or accept and document. Same applies to the calldata-array variants (bounded by calldata size, so lower risk).

### [M-04] `ERC6909` missing zero-address / zero-amount validation and non-standard events
- **Severity:** Medium (Low in this deployment)
- **Vulnerability Type:** Standard non-compliance
- **Impact:** `transfer`/`transferFrom`/`_mint`/`_burn` do not revert for `amount == 0` or `receiver == address(0)` (mint to zero permanently burns with a misleading event). Off-chain indexers and CEX integrations relying on ERC-6909 semantics can misindex. In `PoolManager`, mint/burn of claim tokens is delta-accounted so funds safety is preserved, but `mint(address(0), id, amount)` creates an unbacked-looking claim reduction for the caller with tokens lost.
- **Root Cause & Code Location:** `ERC6909._mint`, `transfer`, `transferFrom`.
- **Remediation:** Add `if (receiver == address(0)) revert();` in `_mint`/`transfer` paths, or document the minimalist deviation (Solmate heritage — intentional).

## Low / Informational

- **[L-01] `collectProtocolFees` rounding:** `amount == 0` collects the full accrued balance; partial amounts are exact — fine, but `protocolFeesAccrued[currency] -= amountCollected` will revert on over-ask rather than clamping; controller error handling only.
- **[L-02] `Pool.swap` `unchecked` protocol-fee arithmetic:** `step.feeAmount -= delta` relies on `delta <= step.feeAmount`; holds given `calculateSwapFee` composition, but is invariant-by-construction only — worth a fuzzing assertion (already covered by v4's fuzz suite).
- **[L-03] `updateTick` assembly packing:** manual `sstore` bypasses Solidity checks; correct as written (liquidityGross ≤ uint128 enforced by `TickLiquidityOverflow` check *after* the store for the lower tick — note the overflow check happens post-write but reverts atomically, so state is safe).
- **[I-01] `Lock`/`CurrencyReserves` transient slots:** collision-resistant via keccak-derived slots; `Exttload` exposes `tload` of *any* slot including `IS_UNLOCKED_SLOT` — read-only, no risk.
- **[I-02] `NoDelegateCall`** correctly uses immutable `original` — cannot be spoofed via proxy.

## Conclusion

No exploitable fund-loss path exists in the provided core contracts. The material risks are **integrator-facing** (M-01 donation inflation, M-02 sync/settle discipline) and should be addressed in router/position-manager code and documentation rather than the core.
