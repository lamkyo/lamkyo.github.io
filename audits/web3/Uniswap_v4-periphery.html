## Medium Severity Findings

### M-01 – Zero‑Address Salt Bypass (Denial‑of‑Service)

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Vulnerability Type** | Logic / Access‑Control flaw |
| **Impact** | An attacker can submit a salt whose lower 20 bytes are `0x000…000` (i.e., `address(0)`). The contract’s `updateBestAddress` function treats this as a *valid* submission because of the condition `saltSubAddress != address(0)`. This allows anyone to lock the competition with a salt that yields an **undeployable address** (the zero address cannot host a contract via `CREATE2`). When `deploy()` is later called, `Create2.deploy` will revert, preventing the legitimate deployer from ever deploying the V4 contract. |
| **Root Cause & Code Location** | `updateBestAddress` (lines 45‑49) – the sender validation logic: <br>`if (saltSubAddress != msg.sender && saltSubAddress != address(0)) revert InvalidSender(...)` |
| **Proof of Concept (Foundry)** | ```solidity
pragma solidity ^0.8.20;
import "forge-std/Test.sol";
import "../src/UniswapV4DeployerCompetition.sol";

contract PoC is Test {
    UniswapV4DeployerCompetition comp;
    bytes32 constant INIT_HASH = keccak256(abi.encodePacked("dummy")); // any hash

    function setUp() public {
        comp = new UniswapV4DeployerCompetition(
            INIT_HASH,
            block.timestamp + 1 days,
            address(this),
            1 days
        );
    }

    function testZeroAddressSaltDoS() public {
        // Salt whose low‑20 bytes are zero
        bytes32 badSalt = bytes32(uint256(0x1111)); // e.g. 0x000…001111
        // This call succeeds because saltSubAddress == address(0)
        comp.updateBestAddress(badSalt);
        // Fast‑forward past competition deadline
        vm.warp(block.timestamp + 2 days);
        // Deploy – will revert because CREATE2 cannot deploy to address(0)
        vm.expectRevert(); // generic revert
        comp.deploy(hex"00"); // bytecode hash matches INIT_HASH
    }
}
``` |
| **Remediation** | Disallow zero‑address salts entirely. Replace the validation with: <br>`if (saltSubAddress == address(0) || saltSubAddress != msg.sender) revert InvalidSender(salt, msg.sender);` <br>Optionally, add a `require(bestAddressSalt != bytes32(0), "no best address submitted")` guard in `deploy()` to ensure a *real* address has been selected before deployment. |
| **References** | ERC‑1820 “Zero address is not a contract”, CREATE2 address derivation rules. |

### M-02 – No Finalisation Guard After Successful Deployment

| Item | Detail |
|------|--------|
| **Severity** | Medium |
| **Vulnerability Type** | Logic / State‑Machine flaw |
| **Impact** | After a successful `deploy()` call, the contract remains **open**: any caller can invoke `deploy()` again with the same `bestAddressSalt` and identical bytecode. The second call will revert because the target address already contains code, wasting gas for the caller and potentially causing confusion for off‑chain tooling that expects a single‑use deployment. In a competitive environment, a malicious actor could repeatedly trigger the revert to **spam** the network or to make it appear that the deployment failed. |
| **Root Cause & Code Location** | `deploy` (lines 61‑78) – there is no state flag (e.g., `bool public deployed`) that is set after the first successful `Create2.deploy`. |
| **Proof of Concept (Foundry)** | ```solidity
function testRepeatedDeploy() public {
    // Assume a valid best salt has been set and competition is over
    comp.updateBestAddress(validSalt);
    vm.warp(block.timestamp + 2 days); // past deadline

    // First deployment – succeeds
    comp.deploy(validBytecode);

    // Second deployment – reverts (address already occupied)
    vm.expectRevert(); // generic revert from CREATE2
    comp.deploy(validBytecode);
}
``` |
| **Remediation** | Add a `bool public deployed;` storage variable. In `deploy()`, after the successful `Create2.deploy`, set `deployed = true;` and guard the function with `require(!deployed, "already deployed");`. Emit an event `Deployed(address deployedAddress, address deployer);` for off‑chain indexing. |
| **References** | OpenZeppelin `Clones` library pattern – single‑use deployment guard. |

## Low / Informational Findings

| # | Observation | Recommendation |
|---|-------------|----------------|
| L-01 | The contract does **not** emit an event on successful deployment (`deploy`). | Emit `event Deployed(address indexed deployedAddress, address indexed deployer);` to aid monitoring. |
| L-02 | `bestAddress()` is a public view that recomputes the address each call. This is fine but could be cached in a `public` variable for gas‑efficiency if called frequently off‑chain. | Optional: store `address public bestAddress;` and update it when `bestAddressSalt` changes. |
| L-03 | The contract uses `Create2.deploy(0, bestAddressSalt, bytecode);` with a zero value. If the target contract expects an initial ETH balance, this will be impossible. | Document that the target V4 contract must be payable‑agnostic or that the deployer should use a wrapper to fund the contract post‑deployment. |
| L-04 | The `updateBestAddress` function allows **any** address to submit a salt that does **not** correspond to the sender (when `saltSubAddress == address(0)`). This is already covered in M‑01, but the broader implication is that the competition can be spammed with arbitrary salts. | Consider adding a modest fee (e.g., payable function) or a rate‑limit (e.g., `mapping(address => uint256) lastSubmission`) to mitigate spam. |

---

# Conclusion
`UniswapV4DeployerCompetition.sol` is a compact, well‑structured contract that correctly uses `CREATE2` and immutable parameters to run a deterministic‑address competition. No critical or high‑severity vulnerabilities were found. The two medium‑severity issues identified are **design‑level** concerns that could be exploited to **deny service** or cause **unnecessary gas waste**. Implementing the recommended mitigations will make the competition robust against malicious participants and improve the developer experience.
