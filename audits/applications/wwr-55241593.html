### 2.2 Core design decisions and their justifications

**API design.** A thin, streaming-first contract. `POST /v1/runs` returns a `run_id`; `GET /v1/runs/{id}/events` is SSE. This decouples client lifetime from inference lifetime — essential when an agent run can take 90 seconds and mobile clients drop connections. Every write is idempotent via a client-supplied `Idempotency-Key` with a 24h Redis-backed dedupe window, so retries after a network partition never double-charge or double-insert.

**Data modeling.** Postgres is the system of record — not a vector DB. Vectors are an index, not a source of truth. Multi-tenancy via row-level security with a `tenant_id` in every table and a session-scoped `SET LOCAL app.tenant_id`, which makes tenant isolation a database guarantee rather than an application convention (and a defensible answer to any enterprise security review). Every table carries `created_at`, `updated_at`, and soft-delete; every mutation emits an append-only audit row.

**Concurrency control.** Optimistic concurrency with a `version` column on mutable aggregates — no read-modify-write races under agent tool calls. Long-running runs use a work queue with `SELECT ... FOR UPDATE SKIP LOCKED` leasing, so N workers scale horizontally without coordination beyond Postgres, and a crashed worker's lease simply expires.

**Caching.** Three tiers, each with a different invalidation story:
1. **Exact-match response cache** (Redis, TTL + explicit invalidation on corpus version bump).
2. **Semantic cache** — embedding-similarity lookup with a conservative threshold (0.97+), scoped per tenant, because a wrong cache hit is worse than a cache miss.
3. **Prefix/KV cache** for provider-side prompt caching — deterministic prompt assembly (stable ordering of system → tools → context) so the provider actually gets cache hits.

**Scalability guarantees.** Stateless app tier, HPA on a custom metric (`queue_depth_per_worker`) rather than CPU, since LLM workloads are I/O-bound and CPU-based autoscaling is famously wrong here. Backpressure is explicit: a queue-depth limit that returns `429` with `Retry-After` rather than letting latency silently degrade into timeouts.

### 2.3 Production readiness

- **CI/CD:** trunk-based, GitHub Actions, with a required check that runs the eval suite against the PR branch and fails on >2% regression in task success or >10% regression in p95 latency. Prompt changes are versioned artifacts (hash-pinned, reviewable diffs), never strings edited in a dashboard.
- **Observability:** OpenTelemetry spans across every hop (HTTP → orchestration → retrieval → model → tool), with `trace_id` propagated into the model provider call. Prometheus metrics: `llm_tokens_total{provider,model,direction}`, `llm_ttft_seconds`, `retrieval_hit_rate`, `agent_steps_per_run`, `cache_hit_ratio{tier}`. Alerts on *shipped* signals — error budget burn, eval drift, provider error rate — not on raw latency alone.
- **Load testing:** k6 against a replay-recorded traffic shape (real prompt length distribution, not synthetic equals), run in a staging environment with a mocked provider at p50/p95/p99 cost profiles. Target: sustained 3× peak with no error-rate change, and a documented breaking point.
- **Zero-downtime deployment:** expand/contract migrations only; blue-green for the app tier; schema changes that are always backward-compatible for one release.
