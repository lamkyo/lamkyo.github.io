**Key decisions:**

| Decision | Rationale |
|---|---|
| **Modular monolith, not microservices** | A pre-PMF marketplace has one team and chaotic requirements. Modules with hard boundaries (enforced via lint rules + dependency graph) let you extract `payments` or `search` into services *when load or team size demands it* — without paying distributed-systems tax on day one. |
| **Next.js for web** | Marketplace = SEO surface (contractor profiles, service-category pages are your top-of-funnel organic acquisition). SSR/ISR + structured data (LocalBusiness/Service schema) is table stakes. |
| **React Native/Expo for mobile** | One codebase, OTA updates via EAS, native modules available (push, deep links, camera for profile photos). Faster than two native stacks for a team your size. |
| **Postgres as the system of record** | Transactions across lead assignment + payment holds + notification dispatch are non-negotiable. Postgres gives you ACID + JSONB (flexible service schemas) + PostGIS (geo matching) + pg_trgm/FTS (search) in one system. |
| **Stripe Connect (destination charges / separate charges & transfers)** | Marketplace payments without becoming a money transmitter. Escrow-like authorization → capture flow for lead fees or job deposits, platform fee on connect accounts, instant payouts optional. |
| **Redis + BullMQ** | Async fan-out (notifications, email/SMS, search indexing, payment webhooks retries) without a Kafka cluster you don't need yet. |

### 2.2 API Design

**Style:** REST with an explicit OpenAPI 3.1 contract, versioned at `/v1`. Contract-first: the OpenAPI spec is the source of truth, codegen'd into TypeScript clients for web/mobile (no drift between docs and reality).

**Core conventions:**

- **Resource-oriented, sub-nested where it aids clarity:** `GET /v1/service-requests/{id}/leads` (bids/interest on a request), `POST /v1/listings/{id}/suspend`
- **Cursor pagination everywhere** (`?cursor=...&limit=25`) — offset pagination breaks on hot lists.
- **Problem+JSON (RFC 9457) errors** — machine-readable `type`, human `detail`, field-level `errors[]`.
- **Idempotency keys on all mutations that touch money or create leads** (`Idempotency-Key` header, stored in Redis/Postgres 24h) — network retries must not double-charge or double-assign a lead.
- **ETag/If-None-Match on read-heavy dashboards.**
- **Auth:** short-lived JWT access tokens (15 min) + rotating refresh tokens (httpOnly, SameSite cookies on web; secure storage on mobile). RBAC claims (`client`, `provider`, `admin`), with resource-level authorization checked server-side on every request.
- **Webhooks out:** signed (`Stripe-Signature`-style HMAC + timestamp), at-least-once with exponential-backoff redelivery and a dead-letter view in admin.

**Representative endpoints:**

```
POST   /v1/auth/register                POST  /v1/service-requests
POST   /v1/auth/login                   GET   /v1/service-requests/{id}
POST   /v1/auth/refresh                 POST  /v1/service-requests/{id}/leads
POST   /v1/auth/mfa/verify              POST  /v1/leads/{id}/accept | /decline
```

### 2.3 Data Modeling (PostgreSQL highlights)

```
users ──┬── profiles (role: client | provider | admin)
        ├── provider_profiles (services[], service_area geography, verification_status)
        ├── listings (category_id, geo, price_model, status)
        ├── service_requests (category, budget_range, status, geo_point)
        │        └── leads (request_id, provider_id, price_quote, status, expires_at)
        ├── jobs (request_id, provider_id, escrow_balance, status)
        │        └── milestones (amount, status: pending|funded|released|disputed)
        ├── reviews (author_id, target_id, rating, moderation_status)
        ├── ad_campaigns ── ad_placements (slot, geo, dates, pricing)
        └── transactions (type: charge|transfer|refund|payout, immutable ledger)
```

Design points that matter:

- **Status machines as CHECK constraints + guarded transitions** (service request: `draft → published → lead_gen → in_review → closed`; leads: `sent → viewed → accepted/declined/expired`). Illegal transitions fail at the DB, not just the app layer.
- **Immutable financial ledger** — `transactions` rows are append-only; balances are derived (`SUM` or materialized view), never mutated in place. Reconciliation and audit become trivial.
- **Lead attribution & expiry:** `leads(provider_id, request_id)` with `UNIQUE` partial index so a provider can't bid twice; `expires_at` + a sweeper job converts expired leads to `expired` and releases any holds.
- **Search:** Postgres FTS (`tsvector` + GIN) + `pg_trgm` for fuzzy names, `PostGIS`/`earthdistance` for "near me." At later scale, outbox → Meilisearch/Typesense for typo-tolerant, faceted search.
- **Row-Level Security** for tenant scoping as defense-in-depth (users can only `SELECT` their own rows even if an app query has a bug).
- **Partitioning:** `transactions` and `notifications` by month once volume warrants.

### 2.4 Concurrency Control

Marketplaces are concurrency games. Specific controls:

1. **Lead assignment race → row lock.** Multiple providers accepting a limited-slot lead: `SELECT ... FOR UPDATE SKIP LOCKED` on the lead row inside a transaction; loser gets a clean 409.
2. **Escrow funding race → optimistic versioning.** `jobs.version` column; `UPDATE ... SET version = version + 1 WHERE id = $1 AND version = $expected` — 0 rows affected → 409 Conflict with a re-fetch hint.
3. **Double-charge protection → idempotency keys** (§2.2) + Stripe idempotent API + a `webhook_events` table with a `UNIQUE(event_id)` so replayed webhooks are no-ops.
4. **Search/filter consistency:** read-your-writes on dashboards via `?consistency=read-your-writes` (route to primary or wait for replica LSN).
5. **Cache stampede protection:** per-key mutex in Redis + `stale-while-revalidate` with jittered TTLs.
6. **Rate limiting:** token bucket in Redis (sliding window per IP + per account), stricter buckets on `POST /service-requests` and lead-accept endpoints
