**Key architectural decisions and their justification:**

1. **Postgres as system of record, Kafka via transactional outbox for events.** Avoids dual-write bugs. Every state change emits an event in the same transaction; a relay publishes to Kafka; projections rebuild read models. This gives me auditability (marketplace/payments need it) and lets search/analytics lag safely.
2. **Go for the hot path (gateway, WS fanout, billing).** Predictable p99, low GC pressure under 100k concurrent sockets, single static binary for boring deploys. TypeScript/Node where the domain is CRUD-shaped and team velocity matters. Python where ranking/LLM orchestration lives. *Language follows the problem, not the resume.*
3. **Multi-tenancy via row-level tenancy + Postgres RLS.** Every table carries `tenant_id`; RLS policies enforce isolation at the database, so a forgotten `WHERE` clause in application code cannot leak data across clients. For Citus-sharded deployments, shard key = `tenant_id`.
4. **Idempotency everywhere money or side effects move.** Client-supplied `Idempotency-Key` → Redis `SETNX` with TTL → request journal. Ledger writes are double-entry and immutable; corrections are compensating transactions, never `UPDATE`.

### 2.3 Data Modeling (core entities)

```sql
-- Tenant isolation enforced at the DB, not just the ORM
ALTER TABLE engagements ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON engagements
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

CREATE TABLE engagements (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id      uuid NOT NULL,
  mission_id     uuid NOT NULL REFERENCES missions(id),
  status         engagement_status NOT NULL DEFAULT 'draft',
  rate_cents     integer NOT NULL CHECK (rate_cents BETWEEN 9000 AND 17000),
  currency       char(3) NOT NULL DEFAULT 'USD',
  version        integer NOT NULL DEFAULT 1,          -- optimistic locking
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_engagements_tenant_status ON engagements (tenant_id, status, updated_at DESC);

-- Transactional outbox: atomic with the business write
CREATE TABLE outbox (
  id            bigserial PRIMARY KEY,
  aggregate_type text NOT NULL,
  aggregate_id   uuid NOT NULL,
  event_type     text NOT NULL,
  payload        jsonb NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now(),
  published_at   timestamptz
);
CREATE INDEX idx_outbox_unpublished ON outbox (id) WHERE published_at IS NULL;
```

### 2.4 Concurrency Control

- **Optimistic (default):** `version` column + `If-Match` ETag. `UPDATE ... SET version = version + 1 WHERE id = $1 AND version = $2`; zero rows → 409 with current state. No lock contention, ideal for human-paced edits.
- **Pessimistic (rare, short):** `SELECT ... FOR UPDATE SKIP LOCKED` for job/queue claiming — workers pull work without stepping on each other.
- **Distributed (payments):** idempotency keys + a Postgres advisory lock scoped per `idempotency_key`, held only for the duration of the ledger write (milliseconds).
- **Presence/fanout:** Redis Lua scripts for atomic presence set updates; consistent-hash WS connections across gateway nodes; cross-node fanout via Redis pub/sub (NATS if fanout volume demands it).

### 2.5 Caching Strategy (and its invalidation)

| Layer | What | TTL / Invalidation |
|---|---|---|
| CDN | Static assets, public profiles | `immutable`, content-hashed filenames |
| App-local (ristretto / LRU) | Hot config, permission graphs | 30–60s TTL, tolerate staleness |
| Redis | Sessions, rate limits, idempotency journal | TTL by semantics |
| Redis (read-through) | Engagement detail, mission detail | Write-through on outbox event; version-tagged keys |
| Postgres | `shared_buffers`, `pg_stat` tuning | Materialized views for analytics |

**Invalidation rule I hold to:** cache keys embed a resource version (`eng:eng_7f3a:v3`). A write bumps the version → old keys age out naturally; no thundering-herd delete fanout. On miss storms I use single-flight + short probabilistic early expiration.

### 2.6 Scalability Guarantees

- **Stateless app tier** behind ALB; horizontal pod autoscaling on p95 latency + queue depth (not just CPU).
- **Postgres:** read replicas with `pgbouncer`; Citus for tenant-based sharding beyond ~10k QPS/write-heavy tenants; partition `events`/`outbox` by month.
- **WebSocket tier:** sticky sessions via consistent hashing; presence state externalized to Redis so any node can rehydrate after a deploy.
- **Kafka consumers:** consumer groups with `max.poll` hygiene; exactly-once *effect* via idempotent handlers (natural keys), not broker-level EOS complexity.
- **SLOs as contracts:** availability 99.9% for API; p95 < 200ms for engagement reads; p99 < 50ms for WS fanout within region. Error budget drives release cadence.
