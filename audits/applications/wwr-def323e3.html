# Engineering Application: Data Scientist II, Infrastructure at Pinterest

## 1. Executive Summary & Value Proposition

I build **measurement systems for infrastructure** — the connective tissue between raw telemetry and the decisions platform teams actually make. My background sits deliberately at the seam this role names: production data pipelines on one side, rigorous experimentation and causal inference on the other. Most candidates are strong in exactly one.

**Why this problem space specifically.** Data Science II on Infrastructure fails in two predictable ways when it fails:

- **The analysis is sound but the data is garbage.** A latency regression "analysis" run on a metric whose definition silently drifted three quarters ago produces a confident, wrong answer. Metric *definitions* are the product; the charts are downstream.
- **The analysis is rigorous but nobody can act on it.** A perfectly identified effect that arrives two weeks after the release is archaeologation, not decision support.

My operating pattern is to fix both ends: make the metric trustworthy and versioned, then make it fast and legible enough that an on-call SRE or a platform PM can use it during, or immediately after, an incident.

The work this role describes — **metric definitions, audited data quality, pipeline contributions, experiment design, ambiguous-to-actionable translation** — is exactly the layer above that substrate. I've operated there.

## 2. Deep Technical Solution Blueprint

### 2.1 The core architectural problem

Infrastructure Data Science at Pinterest scale has one dominant failure mode: **the same quantity is defined differently in four places**, and no one can tell which definition a given dashboard or experiment was computed against.

Symptoms, all of which the job description hints at:

| Symptom | Root cause | Typical (bad) fix |
|---|---|---|
| "The dashboard says p99 is 400ms, the SLO burn alert says 250ms" | Percentile computed over different population filters (client vs. edge vs. origin) | Add a fifth dashboard |
| A regression is declared, then evaporates on re-run | Non-idempotent backfill double-counted late-arriving events | Manual reconciliation |
| Metric silently changes 4% on a refactor week | Definition lived in a dbt model / Airflow DAG, not under review | Nobody notices for a quarter |
| Experiment results can't be trusted for a 0.3% guardrail | Underpowered, no variance reduction, no multiple-testing control | Longer experiment (costs weeks) |

The architectural answer is **metrics as versioned, testable artifacts** — the same discipline we apply to code, applied to the definitions that gate every decision.

### 2.2 Core components

**Component A — Metric Contract Registry (the source of truth)**

A metric is not a number. A metric is a *contract*:

```
MetricContract {
  name, owner, domain, tier, version
  entity:        unit of analysis (request | session | pin | merchant | host)
  population:    inclusion/exclusion predicate, explicit
  numerator/denominator:  explicit SQL fragments, not prose
  unit, direction (lower_is_better / higher_is_better)
  window:        aggregation window + watermark/lateness allowance
  percentiles:   [50, 95, 99] with explicit aggregation method (t-digest vs exact)
  freshness_sla: max tolerable (now - max(event_time))
  coverage_floor: min acceptable population coverage vs. a reference count
  guardrails:    min n, max cardinality, null-rate ceiling
  lineage:       upstream tables + producing DAG
  change_log:    every semantic change, dated, with a reviewer
}
```

Stored as code in the repo, validated in CI, rendered into docs. This is the single mechanism that fixes the "four definitions" problem: **a dashboard or experiment that references a metric must reference a versioned contract.**
