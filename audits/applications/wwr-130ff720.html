### 2.2 Storage zones

#### Raw zone

- Immutable or append-only source data.
- Original payload plus ingestion metadata:
  - `source_system`
  - `source_table`
  - `event_time`
  - `ingested_at`
  - `batch_id`
  - `schema_version`
  - `content_hash`
  - `source_offset` or Kafka/Kinesis position
- Encrypted using AWS KMS.
- Partitioning chosen around high-volume, frequently queried dimensions, not arbitrary calendar partitions alone.
- Lifecycle transitions to Glacier or Intelligent-Tiering where retention permits.

#### Curated zone

- Deduplicated, typed, validated, and business-rule-compliant data.
- Conformed dimensions and facts.
- Explicit data contracts and schema versions.
- Deterministic output paths or table versions.
- Atomic publication using a manifest rename or table metadata commit.

#### Serving zone

- Aggregates, materialized views, feature tables, and low-latency extracts.
- Optimized for known access patterns.
- Row-level or column-level controls where required.
- Separate storage from the raw and curated layers to prevent analytical consumers from depending directly on ingestion artifacts.

### 2.3 Batch ingestion design

Each batch should be represented by a manifest containing:

```json
{
  "pipeline": "customer_profile_batch",
  "source": "crm",
  "source_object": "customers/2025-02-14",
  "batch_id": "01JXYZ...",
  "schema_version": 7,
  "content_hash": "sha256:...",
  "row_count": 184233,
  "partition": {
    "ingestion_date": "2025-02-14"
  }
}
```

Processing rules:

1. Discover source objects.
2. Calculate content hashes.
3. Skip already committed objects.
4. Validate schema and required fields.
5. Normalize and transform records.
6. Write temporary output.
7. Validate output counts and invariants.
8. Commit the output atomically.
9. Emit metrics, lineage, and audit events.
10. Retain failed batch artifacts for replay.

This makes reruns safe and prevents partial results from becoming visible to consumers.

### 2.4 Streaming ingestion and concurrency control

For Kafka or Kinesis:

- Use consumer groups for horizontal scale-out.
- Commit offsets only after successful processing or durable checkpointing.
- Partition records by a stable business key, such as `customer_id`, to preserve per-entity ordering.
- Use event-time processing with a configurable watermark.
- Store dead-letter records with the original payload, error classification, source coordinates, and failure timestamp.
- Make downstream state updates idempotent using:
  - deterministic event identifiers;
  - conditional writes;
  - merge keys;
  - deduplication windows;
  - transactional table commits where supported.

For concurrent consumers, correctness should not depend on a single coordinator process. Each event must be safely retryable and must have a stable key.

### 2.5 Data modeling approach

The exact model depends on the source domain, but the following principles apply:

- Define the business grain before choosing physical tables.
- Use surrogate keys for analytical dimensions.
- Maintain source-system lineage and transformation metadata.
- Model slowly changing dimensions explicitly:
  - Type 1 for corrections and mutable attributes;
  - Type 2 for historical attribute analysis.
- Handle late-arriving facts with event time and ingestion time.
- Separate facts from dimensions and avoid denormalizing operational constraints into analytical tables.
- Maintain separate keys for source identity and warehouse identity.
- Enforce uniqueness only where the business grain requires it.

Example analytical grain:

```text
fct_customer_activity
-------------------
one row per customer_id, event_date, event_type, campaign_id
```

The design should not create a fact table whose grain changes silently between releases. Data contracts should make that failure visible.

### 2.6 API design

The platform should expose governed data products rather than unrestricted table access.

A representative API might support:

```http
GET /v1/customer-profiles/{customer_id}
GET /v1/customer-profiles?updated_since=2025-02-01T00:00:00Z
POST /v1/feature-jobs
GET /v1/jobs/{job_id}
GET /v1/datasets/{dataset_name}/versions
GET /v1/lineage/{dataset_name}
```

Design requirements:

- Cursor-based pagination for large result sets.
- Explicit time zones and ISO-8601 timestamps.
- Idempotency keys for job creation and retryable writes.
- Versioned contracts.
- Request correlation IDs.
- Structured error responses.
- Authentication through corporate identity federation.
- Authorization at API, dataset, and optionally row/column level.
- Asynchronous execution for scans, backfills, and exports.
- Bounded query execution with timeouts and maximum scanned-byte controls.

### 2.7 Caching and performance

Caching should be applied only where measured value justifies invalidation complexity.

Suitable uses include:

- Frequently requested dimension lookups.
- Reference data and country/category mappings.
- Short-lived API response caching.
- Aggregated serving datasets.
- Metadata and schema caches.
- Compiled Spark plans or query templates where supported.

A proposed cache hierarchy is:

1. Glue Data Catalog metadata cache.
2. Small, bounded application cache for hot lookups.
3. Materialized serving tables for expensive aggregations.
4. No cache for correctness-sensitive writes.

Cache keys must include:

- dataset version;
- relevant filter parameters;
- authorization context where results vary by user or tenant;
- schema version.

A cache must never be the only copy of authoritative data.

### 2.8 Scalability and reliability guarantees

The architecture should establish explicit service objectives, for example:

- Pipeline success rate: **99.5% or higher** for scheduled workloads.
- Ingestion durability: **no acknowledged events lost**.
- Freshness:
  - near-real-time feeds: under 15 minutes;
  - hourly feeds: within the hourly SLA;
  - daily feeds: before the agreed reporting cutoff.
- Recovery point objective: determined by source replay capability.
- Recovery time objective: based on batch volume and infrastructure provisioning time.
- Zero data loss for acknowledged writes, achieved through durable event archives and replayable source offsets.

Capacity planning should consider:

- input volume and growth rate;
- peak concurrency;
- skew across partition keys;
- transformation cost;
- data compression and storage efficiency;
- EMR/Spark shuffle volume;
- query concurrency;
- downstream consumer lag;
- cross-region replication requirements.

### 2.9 Security and governance

Controls should include:

- IAM roles scoped to specific buckets, catalogs, queues, and KMS keys.
- Separate roles for ingestion, transformation, serving, and operations.
- Private networking for EMR, ECS services, and databases.
- Security groups with explicit ingress/egress.
- KMS encryption at rest and TLS in transit.
- Secrets Manager or Secrets Manager rotation rather than credentials in source code.
- CloudTrail and Glue catalog access logging.
- S3 bucket policies denying unencrypted or public access.
- PII classification and column-level masking for non-production environments.
- Data retention and deletion workflows.
- Schema and data contract approvals.
- Catalog descriptions, ownership, and lineage metadata.
