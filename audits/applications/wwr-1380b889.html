## 1. Executive Summary & Value Proposition

### 1.1 The problem Dremio is actually hiring for

Read past the bullet list and the requisition describes one system under strain: **a multi-cloud, Java-and-C++ lakehouse monorepo whose CI is the critical path for the entire engineering organisation.** Dremio ships Apache Arrow-based vectorised execution, Apache Iceberg table-format work, a distributed query planner, a Kubernetes-native control plane, and a UI layer — all built with Maven, tested across AWS/GCP/Azure, and released to cloud, hybrid, and on-prem delivery endpoints. That combination produces the three failure modes that kill developer velocity:

1. **Feedback latency** — a Maven multi-module reactor rebuilds and retests far more than the change requires, so a one-line Arrow tweak waits behind a 40-minute integration tier.
2. **Signal noise** — distributed systems tests flake. Flakes get "retried until green," which trains engineers to ignore red and destroys the trust that branch protection depends on.
3. **Environment and credential drift** — three clouds, an on-prem artefact pipeline, and long-lived service-account keys that must be rotated, scoped, and audited.

Dremio's posting names the outcomes precisely — *"keeping our development branches 'green'"*, *"automating processes where manual processes exist"*, *"report out on the status, reliability and robustness of our CI/CD systems."* Those are not infrastructure chores; they are a **product with users (Dremio engineers), an SLO, and a roadmap.** That is exactly how I have built and operated developer platforms.

### 1.3 The 90-day thesis

I will not spend the first quarter writing a strategy document. The plan is **measure, then fix the top three constraints, then make the improvements self-defending:**

- **Days 1–15 — Instrument.** Ship a DORA + CI health scoreboard (queue time, p50/p95 pipeline duration, flake rate, revert rate, MTTR-to-green). You cannot improve "greenness" without a number for it.
- **Days 16–45 — Attack the critical path.** Land affected-module detection and remote build caching behind a flag; measure wall-clock delta per pipeline tier before/after.
- **Days 46–70 — Kill the noise.** Deploy automated flaky-test detection with quarantine hysteresis (code in §3) so that red means *broken*, not *unlucky*.
- **Days 71–90 — Make it durable.** Publish playbooks, embed the tooling in the local dev loop (`docker compose` / one-command inner loop), and hand the scoreboard to the teams as a shared accountability surface.
