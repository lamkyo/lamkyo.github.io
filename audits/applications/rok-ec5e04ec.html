## 2. Deep Technical Solution Blueprint

### 2.1 The system: Customer Success Intelligence Platform (CSIP)

A CSM's leverage is a telemetry pipeline. I would build (or rebuild) the following alongside CS Ops:

```
┌──────────────┐   ┌───────────────┐   ┌────────────────┐   ┌──────────────────┐
│ Sources      │──▶│ Ingestion     │──▶│ Feature Store  │──▶│ Scoring Engine   │
│              │   │ (idempotent)  │   │ (parquet/CH)   │   │ (health + risk)  │
│ Directory    │   │               │   │                │   │                  │
│ Insights API │   │ webhook +     │   │ adoption,      │   │ weighted model   │
│ Device Mgmt  │   │ poll fallback │   │ activity, seat │   │ + explainability │
│ SSO/MFA logs │   │ dedupe keys   │   │ utilization,   │   └────────┬─────────┘
│ Support      │   │ retries/DLQ   │   │ support load   │            │
│ CRM (SFDC)   │   └───────────────┘   └────────────────┘            ▼
│ Product tele │                                              ┌──────────────────┐
└──────────────┘                                              │ Playbooks /      │
                                                              │ Alerting / QBR   │
                                                              │ Report Generator │
                                                              └──────────────────┘
```

**Ingestion.** Prefer webhooks; poll Directory Insights and device APIs as fallback. Every event carries a deterministic `dedupe_key = sha256(org_id + event_type + source_id + event_time)`. At-least-once delivery plus idempotent upserts means exactly-once semantics *downstream* without distributed transactions.

**Data model (core entities).**

```
organizations(id, name, segment ENTERPRISE|COMMERCIAL|SMB, arr_cents, csm_id, tz)
org_users(id, org_id, external_id, status, last_auth_at, mfa_enrolled, sso_bound)
org_devices(id, org_id, os_family, enrolled_at, last_checkin_at, compliant)
adoption_facts(org_id, feature_key, period_start, active_users, licensed_seats)
health_snapshots(org_id, computed_at, score, band, components JSONB, model_version)
risk_signals(org_id, signal_type, severity, detected_at, evidence JSONB, state)
expansion_signals(org_id, signal_type, est_value_cents, rationale, state)
qbr_reports(org_id, period, payload JSONB, generated_at, approved_by)
```

Segment and timezone live on the org, not the user — otherwise "weekly active" means something different for each account and no cross-portfolio benchmark is valid.
