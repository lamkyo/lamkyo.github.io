### 2.3 API Design Principles

#### Consistency

- Resource-oriented URLs such as `/v1/domains/{domain}`
- Consistent JSON field naming and timestamp formats
- ISO 8601 UTC timestamps
- Standard error envelope
- Stable identifiers separated from human-readable names
- Explicit units and definitions for rates, counts, and time windows

#### Pagination

For large collections:

```http
GET /v1/domains/example.com/dns?limit=100&cursor=...
```

The cursor should encode a deterministic ordering key, including a unique tie-breaker to prevent duplicates or omissions when data changes during pagination.

#### Filtering

Filters should be bounded, documented, and query-planner aware:

```http
GET /v1/observations?type=dns&value=example.com&first_seen_after=2025-01-01T00:00:00Z
```

The platform should reject unbounded filters early and return actionable errors rather than allowing expensive queries to consume the entire cluster.

#### Versioning

- Additive changes within a major version where possible
- Explicit deprecation and sunset headers
- Contract tests against SDKs and major customer integrations
- Consumer-driven compatibility tests for high-volume partners
- No breaking changes without migration documentation and customer notification

#### Idempotency

For write-like operations such as saved searches, alerts, exports, or case integrations:

```http
Idempotency-Key: 7e4b...
```

The server should store the request fingerprint and response reference for a defined period, preventing duplicate alert or export creation during client retries.

### 2.4 Data Modeling

A useful design separates four concepts:

1. **Canonical entities**  
   Normalized domains, IP addresses, certificates, ASNs, organizations, and URLs.

2. **Observations**  
   A source-specific record that an entity was observed with a particular value at a particular time.

3. **Derived relationships**  
   Resolver, registration, hosting, certificate, infrastructure, or organizational relationships.

4. **Products and assessments**  
   Risk scores, classifications, detections, recommendations, and customer-facing conclusions.

This separation prevents a derived score or model output from being confused with ground truth. It also allows the system to explain why a result exists.

### 2.5 Freshness, Latency, and Consistency

Different product surfaces require different consistency guarantees:

- Interactive enrichment may use a near-real-time view.
- Passive DNS history may tolerate minutes of ingestion lag while preserving event-time accuracy.
- Bulk exports may be asynchronous and snapshot-consistent.
- Investigations may benefit from an explicit as-of timestamp.
- Risk or classification products may require re-scoring when underlying evidence changes.

I would avoid promising global strong consistency. Instead, I would define consistency per product contract:

```text
Real-time operational APIs:
  Eventual consistency with published freshness SLO

Bulk exports:
  Snapshot at a declared cutoff time

Historical queries:
  Event-time correctness, independent of ingestion delay

Scoring APIs:
  Assessment version plus evidence version
```

### 2.6 Concurrency Control

The platform should combine:

- Idempotent ingestion keys
- Partitioned processing by entity or source
- Optimistic concurrency for mutable customer configuration
- Distributed leases for long-running exports and investigations
- Queue-based backpressure
- Deduplication using content hashes and source identifiers
- Exactly-once business effects where practical, with at-least-once transport underneath

For example, an ingestion event may be delivered more than once, but its derived database mutation should be idempotent:

```text
event_key = source_id + source_event_id
```

A duplicate delivery should acknowledge the existing processed event rather than create a second observation or trigger a duplicate model update.
