## 1. Executive Summary & Value Proposition

Stripe's Abuse Research Group is not a detection team. It is an **offensive research function that produces falsifiable, machine-checkable claims about how money is moved through Stripe's APIs by adversaries** — and then turns those claims into controls and regression tests that make the abuse path structurally unprofitable. That is a systems-engineering problem before it is a security problem: the hard parts are telemetry schema stability, taxonomy versioning, deterministic replay of adversary behavior, and translating research artifacts into CI artifacts.

My background maps onto that problem in three specific ways:

**1. Kill-chain modeling as a first-class data model.** I have spent my career treating multi-stage adversarial processes — not single events — as the unit of analysis. The recurring failure mode in fraud infrastructure is *monolithic risk labels*: a `machine_learning_score > 0.87` attached to a transaction, which tells you nothing about which stage of the exploit was reachable and which control failed to interrupt it. FT3's decomposition of fraud into structured kill chains is architecturally the right move, and my instinct is to immediately model it as a **versioned, queryable graph with immutable TTP identifiers** so that every downstream advisory, control recommendation, and regression test is traceable to a taxonomy node and a taxonomy version.

**2. Agentic simulation with hard guardrails.** The role explicitly centers on agentic automated testing to simulate adversary TTPs. I have built LLM-driven agent loops — planner + tool executor + verifier — and I know where they break: non-determinism in replay, runaway tool budgets, silent egress of production-adjacent data, and unverifiable "the control worked" assertions. The blueprint in §2 treats the simulator as a **sandboxed, budget-metered, idempotency-keyed state machine with a deterministic seed**, so that a simulated kill chain is a *reproducible artifact* you can diff across control deploys.

**3. Research → CI pipeline.** The most valuable output of a research group is not a PDF; it is a test that fails when someone regresses a control. I build for the "advisory → regression scenario → control validation gate" path natively, in the same repositories engineers already ship from.

**Domain alignment:** I work fluently in the exact failure classes named in the preferred qualifications — Account Takeover (session/device-binding anomalies, credential-stuffing bursts across ASN rotation), Card Testing (low-value authorization storms on BIN ranges, `issuer_declined` ratio shifts, velocity across `payment_method` fingerprints), and the onboarding-to-monetization transition that most controls miss entirely because ownership of that path is split across Fraud Ops, Risk, and Onboarding. That cross-functional seam is precisely where FT3 earns its keep.
