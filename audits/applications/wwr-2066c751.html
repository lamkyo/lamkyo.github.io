### 2.2 Data modeling

**Core entities** (star schema, optimized for longitudinal behavioral queries):

- `dim_clinician` — SCD Type 2, keyed on a stable `clinician_sk` (surrogate) with `npi` as a business key. Specialty, geography, affiliation, seniority — all slowly changing.
- `fact_clinician_event` — append-only, partitioned by `event_date` and hash-sharded by `clinician_sk`. Columns: `event_type`, `surface` (app/web/API), `session_id`, `referrer_campaign_id`, `payload` (JSONB, schema-registered).
- `fact_clinician_engagement_daily` — pre-aggregated rollup: sessions, distinct surfaces, content interactions, message sends. This is the table 90% of client analyses read.
- `dim_client_cohort` — the client-facing cohort definition (inclusion/exclusion criteria as versioned SQL), so a cohort is *reproducible* and *auditable*.

**Key modeling decisions:**

1. **Surrogate keys + SCD2 on clinician.** NPIs change affiliations; a client asking "cardiologists at Hospital H" needs point-in-time correctness. Type 2 with `valid_from`/`valid_to` gives us `AS OF` joins without bitemporal complexity.
2. **Late-arriving events.** Mobile clients sync offline. We write to a *staging* partition with `event_ingest_ts` and `event_occurred_ts`, and the dbt model uses a **watermark + reprocessing window** (last 7 days re-derived nightly) so downstream aggregates are eventually correct without full rebuilds.
3. **PII boundary.** Raw payloads never leave the ingestion zone. The feature store operates on tokenized identifiers; re-identification requires a separate, audited service. This is the HIPAA posture that lets legal say yes.

### 2.3 API design

A thin, read-only **Insights API** so commercial teams and (optionally) clients can pull results programmatically instead of waiting on a notebook:

```
GET  /v1/cohorts/{cohort_id}/profiles            → behavioral segment breakdown
GET  /v1/cohorts/{cohort_id}/timeseries?metric=  → engagement over time
POST /v1/models/propensity/score                 → batch scoring (async job)
GET  /v1/jobs/{job_id}                           → job status + signed result URL
GET  /v1/analyses/{analysis_id}/export?fmt=csv   → governed export w/ row caps
```

- **AuthN/Z:** OAuth2 client credentials for internal service callers; JWT with *cohort-scoped* claims for client-facing access. Row-level security enforced at the Postgres layer (`SET app.current_cohort`), not just in application code — so a bug in the API can't leak another client's cohort.
- **Idempotency:** `POST /score` accepts an `Idempotency-Key` header; duplicate submissions within 24h return the original job. Scoring a 200K-clinician cohort twice is expensive and confusing.
- **Async by default:** Anything >2s is a job. `202 Accepted` + `Location` header + polling or webhook callback. Long-running PyTorch inference never blocks a request thread.

### 2.4 Concurrency control

- **Read path:** Stateless API pods; connection pooling via PgBouncer (transaction mode); Redis for hot cohort aggregates with **stale-while-revalidate** (serve cached value, refresh in background if `age > 30s`).
- **Write path:** Feature materialization uses **partition-level optimistic concurrency** — a dbt run claims a `(model, partition, watermark)` row via `INSERT ... ON CONFLICT DO NOTHING`; if another run holds the claim, the newcomer skips. Prevents double-computation without distributed locks.
- **Model scoring:** Batch jobs are sharded by `hash(clinician_sk) % N`; each shard is independently retryable. Exactly-once *effect* achieved via idempotent writes keyed on `(model_version, cohort_id, clinician_sk)`.

### 2.5 Caching strategy

| Layer | What | TTL | Invalidation |
|---|---|---|---|
| CDN | Static viz assets, public docs | 24h | Versioned URLs |
| Redis | Cohort aggregates, segment counts | 30s–5min SWR | Event-driven on cohort edit |
| Postgres | Materialized views (`REFRESH CONCURRENTLY`) | On dbt schedule | Watermark-based |
| In-process | Cohort definition compilation (SQL AST) | 10min | LRU, keyed on definition hash |

Cohort definitions are content-hashed; a definition edit changes the hash, which changes the cache key — **invalidation by construction**, not by bookkeeping.

### 2.6 Scalability guarantees

- **Ingestion:** Kafka partitions keyed by `clinician_sk` → per-clinician ordering guaranteed, horizontal scale by adding partitions. Spark Structured Streaming with checkpointed offsets → at-least-once into the warehouse, idempotent upserts downstream → effectively-once.
- **Warehouse:** Partition pruning on `event_date` + bucketing on `clinician_sk` means a 180-day cohort scan touches only relevant files. Incremental dbt models process only the watermark delta.
- **Serving:** Read replicas for the API; horizontal pod autoscaling on p95 latency; Redis Cluster for cache sharding.
- **Backpressure:** Scoring jobs have a concurrency semaphore per tenant; a runaway client can't starve internal workloads.

### 2.7 Production readiness

**CI/CD:**
- GitHub Actions: lint (`ruff`, `mypy --strict`) → unit (`pytest`, ≥80% on business logic) → integration (Docker Compose: Postgres + Redis + MinIO) → dbt build against a fixture warehouse → container build → deploy to staging → **canary (10%)** → promote.
- Migrations via Alembic; **expand-contract** pattern (add column → backfill → switch reads → drop) so schema changes never break a running pod.
- Model deployments are versioned artifacts (MLflow registry); promotion requires passing a **champion/challenger** offline eval gate and a shadow-deploy period.

**Observability:**
- **OpenTelemetry** traces across API → db → cache, with cohort_id and model_version as span attributes.
- **Prometheus** metrics: `insights_api_request_duration_seconds` (histogram, p50/p95/p99), `feature_freshness_seconds` (gauge — *the* SLO for "is this insight current?"), `scoring_jobs_in_flight`, `dbt_model_run_duration`, `cache_hit_ratio`.
- **SLOs:** 99.5% API availability; feature freshness < 60 min for 99% of models; scoring job success rate > 99%.
- **Alerting:** PagerDuty on SLO burn rate (not raw thresholds); Slack on data-quality anomalies (null-rate spikes, distribution drift via Evidently/Whylogs).

**Load testing:** k6 scripts replaying a synthetic cohort workload (70% reads / 20% exports / 10% scoring submissions); gate on p95 < 400ms at 500 RPS. Nightly perf run in CI with regression budget.

**Zero-downtime deploys:** Rolling update with readiness probes keyed to a `/healthz` that actually checks DB + Redis connectivity; preStop sleep for connection drain; DB migrations run as a separate pre-deploy job using expand-contract so old and new pods coexist safely.
