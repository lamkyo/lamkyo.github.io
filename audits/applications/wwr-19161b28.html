### 2.2 Data Modeling Principles

| Layer | Rule | Rationale |
|---|---|---|
| **staging** | 1:1 with source, no joins, no aggregations | Cheap to rebuild, easy to diff against source |
| **intermediate** | Single-responsibility transforms, fully tested | Reusable across marts; isolates messy logic |
| **marts** | Star schema, surrogate keys, conformed dimensions | BI-friendly, avoids fan-out joins |
| **metrics** | Declarative definitions (dbt semantic layer or LookML) | One number, one definition, everywhere |

**Key modeling decisions for this domain:**
- **Bitemporal subscription facts.** Every subscription state carries `valid_from` / `valid_to` (system time) *and* `effective_from` / `effective_to` (business time). This is non-negotiable for restated revenue and audit trails.
- **Event-sourced MRR/ARR.** Rather than snapshotting ARR, model every state *change* as an MRR event (new, expansion, contraction, churn, reactivation). Snapshots are then a rollup — which makes period-over-period variance a self-answering query.
- **SCD Type 2 for accounts and products.** Product price changes and account hierarchy changes must be historically accurate.
- **Late-arriving data handled explicitly.** Stripe webhooks and Orb usage can land days late; incremental models use a lookback window (`interval '3 days'`) with a `dbt_utils.unique_combination_of_columns` guard.

### 2.3 Concurrency, Caching, and Scalability

- **Snowflake warehouse sizing per layer:** `TRANSFORMING` (dbt, L/XL, auto-suspend 60s) separated from `ANALYTICS` (Looker, M, multi-cluster) and `FINANCE_CLOSE` (XL, dedicated during close windows). This prevents a heavy dbt run from starving month-end reporting.
- **Result caching** is used for BI, but never relied on for financial figures — financial marts set `warehouse` hints to a dedicated warehouse where cache invalidation on `ALTER` is deterministic.
- **Incremental materialization with `merge` strategy** on a bitemporal key; `on_schema_change: sync_all_columns` to survive upstream drift.
- **dbt state comparison (`--select state:modified`)** in CI so only changed models rebuild — critical as the graph grows.
- **Partitioning & clustering:** monthly fact tables clustered by `account_id`; date-partitioned staging for time-series scans.

## 3. Production-Ready Code / Architectural Proof

The following is a realistic slice of the ARR / revenue-recognition pipeline: an intermediate MRR event model, a bitemporal incremental fact, a custom data-quality assertion macro, and the CI workflow.

### 3.1 `models/intermediate/int_mrr_events.sql`

```sql
{{
    config(
        materialized='incremental',
        unique_key='mrr_event_sk',
        incremental_strategy='merge',
        on_schema_change='sync_all_columns',
        cluster_by=['event_month']
    )
}}

/*
    One row per subscription-state change (new / expansion / contraction /
    churn / reactivation), derived from Stripe subscription items joined to
    Orb usage rating for usage-based components.

    Handles:
      - Late-arriving Stripe events (3-day lookback window)
      - Usage-based lines rated by Orb (recognized as they accrue)
      - Currency normalization to USD at the invoice FX rate
      - Idempotency via deterministic surrogate key
*/

with stripe_subscription_items as (

    select
        subscription_item_id,
        subscription_id,
        account_id,
        price_id,
        quantity,
        mrr_cents,
        currency,
        status,
        effective_from,
        effective_to,
        _stg_loaded_at
    from {{ ref('stg_stripe__subscription_items') }}

    {% if is_incremental() %}
    where _stg_loaded_at >= (
        select coalesce(max(_stg_loaded_at), '1900-01-01'::timestamp)
        from {{ this }}
    ) - interval '3 days'
    {% endif %}

),

prior_state as (

    -- Previous known MRR for each subscription item, as-of the event time.
    select
        subscription_item_id,
        mrr_cents as prior_mrr_cents,
        effective_from as prior_effective_from
    from {{ ref('int_mrr_events') }}
    where effective_from < (select min(effective_from) from stripe_subscription_items)

),

usage_rated as (

    select
        subscription_item_id,
        sum(usage_amount_cents) as usage_mrr_cents,
        min(period_start)       as usage_period_start
    from {{ ref('stg_orb__rated_usage') }}
    where rating_status = 'final'
    {% if is_incremental() %}
      and period_start >= (select coalesce(max(event_month), '1900-01-01') from {{ this }})
    {% endif %}
    group by 1

),

classified as (

    select
        s.subscription_item_id,
        s.subscription_id,
        s.account_id,
        s.price_id,
        s.effective_from,
        s.effective_to,
        s._stg_loaded_at,

        coalesce(s.mrr_cents, 0) + coalesce(u.usage_mrr_cents, 0) as current_mrr_cents,
        coalesce(p.prior_mrr_cents, 0)                            as prior_mrr_cents,

        case
            when p.subscription_item_id is null and s.status = 'active' then 'new'
            when p.subscription_item_id is null and s.status in ('canceled','incomplete_expired') then 'churn'
            when p.prior_mrr_cents = 0 and coalesce(s.mrr_cents,0) > 0 then 'reactivation'
            when coalesce(s.mrr_cents,0) > p.prior_mrr_cents then 'expansion'
            when coalesce(s.mrr_cents,0) < p.prior_mrr_cents then 'contraction'
            when s.status in ('canceled','incomplete_expired') then 'churn'
            else 'no_change'
        end as event_type

    from stripe_subscription_items s
    left join prior_state p using (subscription_item_id)
    left join usage_rated  u using (subscription_item_id)

)

select
    -- Deterministic key: same event replayed → same key → idempotent merge
    {{ dbt_utils.generate_surrogate_key([
        'subscription_item_id',
        'effective_from',
        'event_type'
    ]) }} as mrr_event_sk,

    {{ dbt_utils.date_trunc('month', 'effective_from') }} as event_month,
    account_id,
    subscription_id,
    subscription_item_id,
    price_id,
    event_type,
    prior_mrr_cents,
    current_mrr_cents,
    current_mrr_cents - prior_mrr_cents as delta_mrr_cents,
    effective_from,
    effective_to,
    _stg_loaded_at as source_loaded_at,
    {{ dbt_utils.current_timestamp() }} as dbt_loaded_at

from classified
where event_type != 'no_change'
```

### 3.2 `models/marts/finance/fct_arr_monthly.sql`

```sql
{{
    config(
        materialized='incremental',
        unique_key='month_key',
        incremental_strategy='merge',
        cluster_by=['month_start']
    )
}}

/*
    Monthly ARR snapshot with full waterfall reconciliation.

    ARR = MRR at month-end × 12 (annualized, excluding one-time fees).

    Guarantees:
      - Waterfall identity holds: begin + new + expansion − contraction − churn = end
      - Restatement-safe: re-running a historical month overwrites it deterministically
      - Bitemporal: carries both business-effective and system-load timestamps
*/

with months as (

    select
        date_trunc('month', month_start)::date as month_start
    from {{ ref('dim_date') }}
    where month_start >= '2019-01-01'
      and month_start <= current_date()

),

events as (

    select
        event_month,
        sum(case when event_type = 'new'         then delta_mrr_cents else 0 end) as new_mrr_cents,
        sum(case when event_type = 'expansion'   then delta_mrr_cents else 0 end) as expansion_mrr
