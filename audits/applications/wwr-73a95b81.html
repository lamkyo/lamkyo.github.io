## 2. Deep Technical Solution Blueprint

### 2.1 System context

A suitable logical architecture for Edfinity would preserve Rails as the primary product and integration boundary while making high-volume and asynchronous behavior explicit:

```text
Educator / Student / LMS
          |
      React UI
          |
   Rails API / BFF
      |       |       \
MongoDB   Redis    Elasticsearch
      |
  Sidekiq jobs
   |       |       \
LLM      ClickHouse  External services
providers
```

The important design principle is that the Rails application owns product invariants and authorization, while workers own interruptible, retryable, and potentially long-running work.

### 2.2 Assessment and grading domain model

I would model the assessment lifecycle explicitly rather than using a single mutable “assessment” document for every concern.

#### Core entities

- **Course or course offering:** The tenant and academic context.
- **Assessment:** Stable identity, version, publication state, and authoring metadata.
- **AssessmentVersion:** Immutable published content or a controlled versioned representation.
- **Item or Question:** The gradeable unit, including type, rubric references, metadata, and validation rules.
- **Attempt:** A student’s execution of an assessment.
- **Submission:** A submitted response, artifact, or answer set.
- **Grade:** A scored result, rubric outcome, and feedback bundle.
- **GradingJob:** An asynchronous execution record with provider/model/prompt versions.
- **IntegrationDelivery:** LMS delivery state and external identifiers.
- **AuditEvent:** Append-only record of meaningful state transitions.

#### State transitions

```text
assessment:
  draft -> in_review -> published -> archived

attempt:
  created -> in_progress -> submitted -> grading
                              -> graded
                              -> needs_review

submission:
  accepted -> processing -> processed
                          -> rejected
```

Transitions should be validated by domain services. Controllers should not contain arbitrary status updates.

### 2.3 MongoDB design

MongoDB should be optimized for the query patterns required by the product.

For example, an attempt might look conceptually like:

```json
{
  "_id": "attempt_123",
  "tenant_id": "tenant_456",
  "assessment_version_id": "assessment_version_789",
  "student_id": "student_abc",
  "status": "submitted",
  "attempt_number": 2,
  "version": 7,
  "submitted_at": "2026-02-20T14:03:11Z",
  "created_at": "2026-02-20T13:45:00Z"
}
```

Recommended indexes would be driven by measured access patterns:

```js
db.attempts.create_index(
  { tenant_id: 1, assessment_version_id: 1, student_id: 1, attempt_number: -1 },
  { unique: true, name: "unique_attempt_per_student_version" }
)

db.attempts.create_index(
  { tenant_id: 1, status: 1, updated_at: 1 },
  { name: "tenant_status_updated_at" }
)
```

Design rules:

- Every tenant-owned query includes `tenant_id`.
- Compound-index order reflects actual filters and sort order.
- Embedded data is used only when it has the same ownership, lifecycle, and bounded growth.
- Large submissions, generated artifacts, and model outputs should be stored outside frequently queried documents.
- Published assessment content is immutable where practical.
- Schema validation is applied at the application boundary and, where supported, in MongoDB.
- Uniqueness is enforced by database indexes rather than only application checks.

### 2.4 API design

External APIs should use resource-oriented endpoints with explicit idempotency and version semantics.

Examples:

```http
POST /v1/attempts
Idempotency-Key: 8f3c...
Content-Type: application/json
```

```http
GET /v1/attempts/:attempt_id
```

```http
POST /v1/attempts/:attempt_id/submissions
Idempotency-Key: 4f21...
```

```http
POST /v1/attempts/:attempt_id/grade
```

```http
GET /v1/grading-jobs/:grading_job_id
```

API response conventions:

- Stable error codes independent of human-readable messages.
- Request IDs echoed into logs, traces, and audit events.
- Explicit pagination for collections.
- Idempotency keys on externally initiated or retried writes.
- Maximum request sizes enforced before expensive parsing or storage.
- No internal stack traces, prompts, or provider responses returned to clients.

Example error format:

```json
{
  "error": {
    "code": "attempt_already_submitted",
    "message": "This attempt has already been submitted.",
    "request_id": "req_01J4Z0Q4T4"
  }
}
```

### 2.5 Concurrency control and idempotency

High-value writes should use both optimistic concurrency and idempotency.

#### Optimistic concurrency

Include a monotonically increasing `version` field on mutable documents. Update with a compare-and-set predicate:

```ruby
result = Attempt.where(
  id: attempt_id,
  version: expected_version,
  status: "in_progress"
).update_all(
  status: "submitted",
  submitted_at: Time.current,
  version: expected_version + 1
)

raise ConcurrentModification if result.zero?
```

This prevents two browser tabs, LMS callbacks, or workers from silently overwriting one another.

#### Idempotency

For submission and grading requests:

1. Hash the tenant, endpoint, principal, and idempotency key.
2. Store the request fingerprint and response snapshot.
3. Return the original response for an identical retry.
4. Reject reuse of the same key with a different payload.
5. Expire records according to business and privacy requirements.

For asynchronous jobs, the job ID and domain transition must both be durable. A retry should not create a second grade or send a second integration callback.

### 2.6 Asynchronous grading workflow

A safe AI-assisted grading flow should look like this:

```text
1. Validate attempt ownership and state.
2. Persist a GradingJob in pending state.
3. Enqueue a Sidekiq job with a deterministic job key.
4. Worker claims the job and transitions it to running.
5. Normalize and redact the submission.
6. Retrieve only authorized rubric/context data.
7. Call the model with a versioned prompt and structured schema.
8. Validate the response.
9. Apply deterministic scoring and rubric rules.
10. Persist the grade and audit event transactionally.
11. Enqueue notifications and analytics projections.
12. Mark the job complete.
```

Important safeguards:

- Model output is untrusted input, even when generated by an internal provider.
- JSON or tool results are schema-validated before use.
- Raw model output is retained only according to privacy policy.
- Prompt and model versions are recorded for reproducibility.
- A confidence threshold can route uncertain work to human review.
- A timeout or provider outage must not corrupt an attempt.
- Retryable failures use exponential backoff with jitter.
- Non-retryable validation failures go to a reviewable terminal state.

### 2.7 Elasticsearch strategy

Search should be modeled as a projection, not as the system of record.

A robust indexing flow is:

```text
MongoDB transaction
    -> outbox event
        -> indexing worker
            -> Elasticsearch document
```

The outbox prevents the classic dual-write failure where MongoDB commits but the search document is lost.

Search documents should include only the fields required for search and display:

- Tenant and authorization scope.
- Assessment title and metadata.
- Normalized question/prompt text.
- Tags and course identifiers.
- Content version.
- Visibility state.
- Index timestamp.

Deleting or unpublishing content should generate a corresponding projection event. Periodic reconciliation should compare MongoDB source state with indexed documents.

### 2.8 ClickHouse analytics

ClickHouse should be used for high-volume, append-oriented analysis rather than transactional product reads.

Examples of useful event streams:

- Assessment opened and submitted.
- Grading job queued, started, completed, failed, or manually reviewed.
- Model latency and token/cost metrics.
- Rubric score distribution.
- LMS delivery success and retry counts.
- Educator authoring activity.
- Student feedback and review events.
