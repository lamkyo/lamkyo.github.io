## 2. Deep Technical Solution Blueprint

### 2.1 Framing the primary system requirement

The recurring architectural problem in Mirantis's product surface — and the one I would expect this role to own — is:

> **Declaratively reconcile a heterogeneous fleet of GPU-enabled Kubernetes clusters across sovereign/air-gapped environments, with deterministic, auditable, and reversible provisioning — while keeping a single management plane responsive under partial failure.**

Three forces make this hard simultaneously:

1. **Idempotency across an unreliable, eventually-consistent cloud/hardware API.** Bare-metal and GPU provisioning (MAAS, OpenStack Ironic, cloud GPU APIs) partially fails *constantly*. A controller that is not explicitly designed for partial failure will leak nodes, orphan volumes, and double-charge customers.
2. **Scale of the management plane.** If one control plane manages *N* child clusters × *M* resources, the API server's watch fan-out and the controller's cache memory become the binding constraints long before CPU does.
3. **Sovereignty/air-gap.** No image pulls from public registries, no telemetry exfiltration, no "phone home" licensing. Signatures must verify offline against a pinned trust root.

### 2.3 Core components

**API design.** Keep the API *narrow and declarative*. Three CRDs, each with `spec` fully declarative and `status` carrying only observed state plus a typed `conditions` array (`Ready`, `Provisioning`, `Degraded`, `Stalled`) using the standard `metav1.Condition` shape so `kubectl wait --for=condition` and every existing tooling assumption works unchanged. Never encode intent in annotations; annotations are for consumers, not controllers.

Key API-design rules I enforce:
- **No field is both defaulted and required.** Defaulting happens in the webhook so clients can omit; validation rejects contradiction.
- **Immutable fields are explicitly `+kubebuilder:validation:XValidation:rule="self == oldSelf"`** (CEL, available since 1.25) so the API server enforces immutability rather than the reconciler silently fighting the user.
- **Every mutating field documents its blast radius.** Changing `spec.gpuPool.topology` on a live pool is a disruptive operation and the CRD should say so.

**Data modeling.** The critical modeling decision is the **stateless-intent / stateful-observation split**:

| Layer | Storage | Rationale |
|---|---|---|
| Desired state (spec) | etcd via CRD | Single source of truth, GitOps-diffable |
| Observed infra state | `status` + provider tags/labels | Must survive controller restarts → authoritative tag on the *provider* resource, e.g. `mirantis.io/owner-uid=` |
| Intermediate provisioning state | **Recomputed on every reconcile, never persisted** | Persisting a "wing in progress" flag guarantees divergence after a crash |
| Provider inventory (catalog) | In-memory TTL cache | Read-heavy, short-lived, expensive upstream |

The single most important rule: **the provider resource's own tags are the system of record for ownership.** A controller that keeps ownership only in its own memory will, after a crash mid-provision, forget it created a node and will never clean it up. Tagging the remote object with the owning CR's UID makes orphan detection a *query* rather than a *memory* — which is what makes the "reversible and auditable" guarantee real.

**Concurrency control.** Four distinct layers, each solving a different problem:

1. **Workqueue-level:** `controller-runtime`'s per-key serialization guarantees no two goroutines reconcile the same CR simultaneously. I raise `MaxConcurrentReconciles` to a *measured* value (4–8 for I/O-bound provider controllers), never unbounded — provider APIs rate-limit and an unbounded reconciler turns a rate limit into a retry storm.
2. **Optimistic concurrency on status:** every `Status().Update()` carries the `resourceVersion` read at reconcile start. Conflicts are handled by **requeueing, never by `RetryOnConflict` loops that re-read and blindly re-apply** — blind re-apply is how controllers resurrect state a user just deleted.
