## 1. Executive Summary & Value Proposition

### 1.1 The problem, stated precisely

This engagement is not "build a Power App." It is a **decision-grade architecture assessment** of a legacy Power Platform estate whose integration boundary is unstable. Three properties make it hard:

1. **The data-profiling spike (Regulatory) is on the critical path.** You cannot choose Dataverse entity granularity, indexing strategy, or capacity model until you know cardinality, multiplicities, and PII/retention classification of the regulatory dataset. Architecting before profiling means architecting twice.
2. **Four integration touchpoints are under-specified.** Counterparty APIs that are "uncertain, changing, or being migrated" break the default assumption of every low-code integration pattern: that the remote contract is a constant. The architecture must treat the *counterparty contract as a variable*.
3. **Licensing is an architectural constraint, not a procurement afterthought.** A model choice that adds an unlicensed audience segment (Power Pages) or an extra Dataverse per-user app changes the run-rate by five figures annually. Licensing must be a first-class input to the design, evaluated in the same document as the ERD.

## 2. Deep Technical Solution Blueprint

### 2.1 Phase 1 Assessment Methodology (Weeks 1–2)

The assessment is a **dependency-graph extraction**, not a code read.

**Artifact inventory and static analysis**
- Unpack every solution (unmanaged export → `pac solution unpack --processCanvasApps`) to recover canvas app `Src/`, flow definitions, environment variables, and connection references. Canvas apps are not reviewable in the Maker portal at scale; the unpacked YAML/JSON is.
- Build a **dependency graph**: environment variable → connection reference → connection → connector → external endpoint. This surfaces the hidden dependency that kills rewrites: a cloud flow bound to a *user's personal connection* to a system that has no service principal.
- Run Solution Checker (Ruleset: Solution Checker) and triage findings into (a) security, (b) performance/delegation, (c) deprecated API usage, (d) unused components.

**Runtime evidence, not opinion**
- Application Insights / Dataverse telemetry (if present) → p50/p95 latency by operation, plugin execution time, top-20 slowest Flows.
- If absent, we instrument: a short-lived audit that captures `OrganizationRequest` volume by user, to size service-protection headroom.
- Dataverse row counts and table-size distribution via the `RetrieveTotalRecordCount` / `PrincipalObjectAccess` data → the real basis for capacity and indexing decisions.

**Anti-pattern catalog with severity.** Every finding gets: *finding → evidence → blast radius → remediation cost → whether it blocks the rebuild option*. This is the document that makes the patch-vs-rebuild decision defensible.

Target deliverable: a **Current-State Architecture & Findings Register**, with a dependency graph, a risk-weighted findings table, and a licensing baseline (current entitlement vs. actual consumption).
