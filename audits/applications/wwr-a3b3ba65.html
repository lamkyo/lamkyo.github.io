## 2. Deep Technical Solution Blueprint

### 2.1 Proposed Program: Account Security Control Plane

I would propose a unified account-security architecture centered around a security-critical **Account Security Service** that exposes narrowly scoped, strongly authenticated APIs to web, mobile, desktop, and internal product services.

The service would own the security-sensitive state for:

- Authentication ceremonies.
- Passkey/WebAuthn registration and authentication.
- MFA enrollment and verification.
- Session issuance, rotation, revocation, and device binding.
- Recovery initiation and approval.
- Authentication risk signals.
- Account-security events and audit records.
- Administrative and self-service account-protection actions.

The design should avoid making this service a monolithic synchronous dependency. Instead, use a control-plane/data-plane split:

```text
Clients and Product Services
          |

  Edge / API Gateway / mTLS
          |
          v
Account Security API
  |          |           |
  v          v           v

  |          |           |
  +----------+-----------+
             |
             v
      Account Security Store
   (replicated relational data)
             |

     Event / Audit Pipeline
             |

    SIEM, Detection, Analytics
```

### 2.2 Primary Authentication Flow

A typical passkey login would be handled as follows:

1. Client submits a login request containing an opaque request identifier and minimum contextual metadata.
2. Account Security Service verifies that the request:
   - Was created by a trusted client or product service.
   - Has not expired.
   - Has not already been consumed.
   - Is bound to the intended authentication flow.
3. Service returns a WebAuthn challenge and allowable credential metadata.
4. Client completes the WebAuthn ceremony.
5. Server validates:
   - Origin and RP ID hash.
   - Client-data JSON.
   - Authenticator data.
   - Signature counter behavior where available.
   - User-presence and user-verification flags required by the ceremony.
   - Credential public-key ownership.
   - Challenge freshness and replay status.
6. The service performs risk evaluation using a low-latency policy path.
7. Session material is minted through a dedicated session issuer.
8. The authentication result is written atomically with session creation and an audit event.
9. Clients receive only the minimum session information necessary.

For high-risk flows, the service can require a step-up challenge or fallback challenge without exposing whether a particular account or credential exists.

### 2.3 Session Security Model

Sessions should use an explicit lifecycle rather than treating a bearer token as an indefinitely valid credential.

Recommended properties:

- Short-lived access credentials.
- Opaque, revocable session identifiers where practical.
- Rotating refresh credentials.
- Reuse detection for rotated refresh credentials.
- Device and client binding signals.
- Server-side revocation checks for sensitive operations.
- Risk-aware step-up authentication.
- Explicit session states such as:
  - `ACTIVE`
  - `ROTATING`
  - `REVOKED`
  - `EXPIRED`
  - `COMPROMISED`
- Maximum lifetime and idle timeout.
- Separate session classes for browser, desktop, mobile, and administrative workflows.

A session record should include a server-side session family. When a refresh credential is used, rotation occurs within a transaction:

```text
lookup refresh token
verify token hash
verify family and session status
mark old token as consumed
create replacement token
persist rotation event
```

If a consumed token is presented again, the entire token family should be revoked rather than returning a generic error that allows an attacker to continue probing.

### 2.4 API Design

The exact transport would align with Discord’s existing service conventions, but the security boundary should expose small, explicit operations.

Representative endpoints:

```http
POST /v1/auth/challenges
POST /v1/auth/webauthn/verify
POST /v1/auth/mfa/verify
POST /v1/sessions
POST /v1/sessions/refresh
DELETE /v1/sessions/{session_id}
POST /v1/sessions/{session_id}/step-up
POST /v1/recovery/challenges
POST /v1/recovery/verify
GET  /v1/account/security/status
POST /v1/account/security/credentials/{credential_id}/revoke
```

Important API properties:

- Idempotency keys for state-changing operations.
- No sensitive secrets in URLs.
- Structured error codes independent of sensitive account existence.
- Strict request and response size limits.
- Request correlation IDs propagated through downstream calls.
- mTLS or workload identity for internal callers.
- Per-service authorization and audience restrictions.
- Explicit anti-replay protection for every ceremony.
- Rate limits partitioned by account, device, IP risk, and operation.
- Constant-time or normalized handling where comparisons are security-sensitive.

Example error response:

```json
{
  "error": {
    "code": "AUTHENTICATION_FAILED",
    "request_id": "req_01J...",
    "retryable": false
  }
}
```

The service should not reveal whether an account exists, whether a particular passkey is registered, or whether recovery is possible until the caller has passed the appropriate policy checks.

### 2.6 Concurrency and Consistency

Security operations should use explicit consistency boundaries.

#### WebAuthn challenge consumption

Challenge consumption must be atomic:

```sql
UPDATE auth_challenges
SET consumed_at = NOW()
WHERE challenge_id = $1
  AND consumed_at IS NULL
  AND expires_at > NOW()
```

The update should affect exactly one row. This prevents two concurrent requests from successfully consuming the same challenge.

#### Refresh-token rotation

Refresh rotation should be executed as a transaction:

1. Lock or compare-and-swap the current token record.
2. Verify the token hash and expiration.
3. Confirm the session is active.
4. Mark the current token as consumed.
5. Insert the successor token in the same transaction.
6. Commit the rotation event.

A duplicate use of a consumed token should trigger family revocation and a security event.

#### Credential revocation

Credential revocation should be:

- Idempotent.
- Immediate for sensitive operations.
- Propagated to session and authorization caches through invalidation events.
- Represented in an immutable audit record.

#### Recovery races

Only one recovery attempt should be authoritative for a given user and flow generation. Competing approvals should result in a controlled denial or invalidation, never an ambiguous state.

### 2.7 Caching and Performance

Caching should improve scale without becoming a source of authorization truth.

Suitable cache use:

- Public key metadata for credential lookup.
- Account-security status projections.
- Risk-policy configuration.
- Short-lived rate-limit counters.
- Non-sensitive client capability data.

Unsafe cache use:

- Authorization decisions for revoked sessions.
- Recovery approvals.
- One-time challenges.
- Refresh-token validity.
- High-risk step-up decisions unless TTL and revocation semantics are explicit.

Recommended invalidation strategy:

- Versioned cache keys by credential or session generation.
- Event-driven invalidation for revocation.
- Short TTLs as a safety net.
- Cache stampede protection using request coalescing.
- Separate hit, miss, stale-read, and invalidation metrics.

### 2.8 Risk-Aware Authentication

Risk scoring should assist policy, not replace it.

Possible signals include:

- Impossible travel.
- New device or client fingerprint.
- ASN or network reputation.
- Authentication velocity.
- Repeated failed attempts.
- Credential-stuffing patterns.
- Changes to recovery channels.
- Session reuse
