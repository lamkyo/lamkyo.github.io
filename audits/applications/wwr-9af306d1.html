### 2.2 Salesforce architecture principles

#### A. Configuration first, code where necessary

I would use declarative Salesforce capabilities when they provide the best balance of maintainability and control:

- **Flow** for orchestration, approvals, notifications, and business state transitions.
- **Validation rules and formulas** for immediate data-quality enforcement.
- **Record Types and permission sets** for business variants.
- **Custom metadata types** for environment-aware configuration.
- **Permission sets and restriction rules** for authorization.
- **Dynamic-related lists and record validation rules** for user-facing data integrity.

Apex would be introduced where Salesforce requires procedural logic, bulk processing, transactional control, complex aggregation, reusable service behavior, or integration-specific handling.

This avoids an overly binary “Flow versus Apex” debate. The standard would be:

> Use the simplest mechanism that reliably satisfies the business requirement, and make the selected mechanism observable and testable.

#### B. Explicit transactional boundaries

Flows and Apex must not create hidden side effects across unrelated business operations. Each transaction should have a documented consistency boundary.

For asynchronous workflows:

- Use Platform Events, Queueable Apex, or Batch Apex where appropriate.
- Make consumers idempotent.
- Persist correlation IDs and business idempotency keys.
- Route failures to an observable retry or dead-letter workflow.
- Avoid recursive Flow execution and uncontrolled trigger loops.
- Apply governor-limit, heap, CPU, and query-bulk safeguards.

For synchronous integrations:

- Define timeout and retry policies per endpoint.
- Avoid external calls inside large transactions where possible.
- Keep integrations resilient to duplicate callbacks and out-of-order events.
- Store technical correlation identifiers separately from business identifiers.

#### C. Secure by default

Security would be designed as a platform property, not a post-deployment checklist.

Key controls:

- Named Credentials instead of secrets embedded in metadata.
- Least-privilege permission sets.
- Restriction rules for record access.
- Sharing rules only where declarative sharing is the correct business model.
- Explicit elevated-access controls and audit trails.
- Session and MFA policy alignment.
- Regular access reviews and dormant-user removal.
- Separation of duties for deployment, approval, and production access.
- Protected metadata and controlled destructive changes.
- Data classification and retention rules for customer, employee, and operational information.

For Experience Cloud, I would separately review:

- Site and guest-user behavior.
- Partner or customer identity boundaries.
- Sharing defaults.
- Apex and Flow security.
- Data exposure through Lightning components.
- Contact and case visibility.
- Abuse monitoring and authentication controls.

#### D. API and integration design

The integration layer would be standardized around versioned, asynchronous where possible, and idempotent contracts.

#### Integration pattern

```text
Source system
    ↓
Authenticated adapter
    ↓
Canonical business event or request
    ↓
Validation and authorization
    ↓
Idempotency check
    ↓
Domain transaction
    ↓
Acknowledgement / retry / dead-letter path
    ↓
Telemetry and audit record
```

For inbound REST or platform events:

1. Authenticate the caller.
2. Normalize the payload.
3. Validate the schema.
4. Reject invalid or unauthorized requests.
5. Calculate an idempotency key.
6. Persist the request or event.
7. Process within a controlled transaction boundary.
8. Record the result and telemetry.
9. Return a deterministic response.

For outbound integrations:

- Use named credentials and least-privilege scopes.
- Apply circuit breakers and exponential backoff where appropriate.
- Do not blindly retry non-idempotent operations.
- Track delivery attempts and terminal failures.
- Reconcile uncertain outcomes asynchronously.
- Expose integration health through dashboards and alerts.

### 2.4 Flow architecture

Flow would be treated as a governed application layer, not merely a collection of automations.

Each production Flow should have:

- A clear business purpose.
- Named owner.
- Version and change history.
- Input and output contract.
- Failure handling.
- Volume assumptions.
- Security review.
- Test evidence.
- Documentation.
- Monitoring or alerting criteria.

I would establish Flow standards covering:

- Trigger entry points.
- Bulk-safe behavior.
- Avoidance of recursive updates.
- Error paths.
- Approval semantics.
- Scheduled and paused-interview behavior.
- Transaction-safe record locking patterns where needed.
- Separation of orchestration from domain logic.

For high-volume or critical business processes, I would use Apex services behind Flow where procedural control is more appropriate.

### 2.5 Concurrency and consistency

Salesforce has strong transactional guarantees within a transaction, but distributed business processes still require explicit design.

I would use:

- **Database locks** only when necessary to prevent conflicting updates.
- **Optimistic concurrency through version fields or timestamps** for user-facing long transactions.
- **Idempotency keys** for integrations and asynchronous work.
- **Apex locking patterns** for queue-safe processing.
- **Platform Events** for decoupled domain notifications.
- **Retry metadata** and terminal-failure handling.
- **Reconciliation jobs** where external systems may be temporarily unavailable.

Example:

```text
Order received
  → Create order in Pending state
  → Validate customer and product data
  → Submit to ERP asynchronously
  → Store external request ID
  → Receive callback
  → Verify authenticity and idempotency
  → Transition order to Confirmed or Exception
  → Emit notification and audit event
```

This avoids pretending that a synchronous HTTP call and a large database transaction are indefinitely reliable together.

### 2.6 Caching and performance

Caching would be used selectively. Salesforce provides platform cache and org cache, but every cached object requires an invalidation and ownership strategy.

I would:

- Cache expensive, stable reference data such as controlled configuration.
- Avoid caching security-sensitive data longer than required.
- Include tenant and user context where needed.
- Define TTL and invalidation behavior.
- Monitor hit rate, stale-data risk, and serialization failures.
- Use query optimization and selective SOQL before introducing custom caching.
- Avoid caching large record collections in user-interface components.

LWC components would use Lightning Data Service for standard record access and Apex only for operations that cannot be expressed declaratively.
