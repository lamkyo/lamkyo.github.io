## 2. Deep Technical Solution Blueprint

### 2.1 Architectural stance

I would build this as a **three-plane system**, deliberately decoupled so that each plane can fail independently:

| Plane | Responsibility | Failure mode tolerated |
|---|---|---|
| **Ingest plane** | Collect, buffer, deduplicate, persist raw | Backpressure, producer restarts, source outages |
| **Normalize plane** | Map raw → canonical schema, enrich, redact | Schema drift, malformed records, enrichment provider downtime |
| **Serve plane** | Query, detect, correlate, expose API | Read-path latency spikes, hot-partition skew |

The invariant: **raw events are immutable and always persisted before normalization is attempted.** If the normalizer is wrong or a vendor changes a field name, you re-derive from raw. Any design that discards the source record is a design that eventually requires the customer to re-ship history.

### 2.2 Core components

**Ingestion.** Sources write to a Kafka/Redpanda topic keyed by `(tenant_id, source_id)` to preserve per-source ordering without forcing global ordering (which would be a throughput ceiling). Producers are transactional; consumers commit offsets only after downstream acknowledgement. Deduplication uses a `(tenant_id, source_id, event_hash, bucket_minute)` key in Redis with a short TTL — bounded memory, and collisions across tenants are impossible by construction.

**Canonical data model** (simplified, ECS/OCSF-influenced):

```python
@dataclass(frozen=True, slots=True)
class NormalizedEvent:
    # Identity & provenance
    event_id: str                    # UUIDv7 — time-sortable, no coordination needed
    tenant_id: str
    source_id: str
    source_type: Literal["windows_security", "sysmon", "linux_auditd", "cloudtrail", "custom"]
    ingested_at: datetime            # pipeline wall clock
    occurred_at: datetime            # source-asserted time, may be skewed/untrusted
    time_confidence: Literal["high", "medium", "low"]  # drives latency vs. correctness tradeoff

    # Classification
    action: str                      # "process_start", "auth_failure", "registry_modify"
    outcome: Literal["success", "failure", "unknown"]
    severity: int                    # 0-100, normalized, not vendor-native

    # Actor / target graph — the part detections actually join on
    actor: ActorRef                  # user, process, or service identity
    target: ActorRef | None
    host: HostRef
    network: NetworkRef | None

    # Escape hatch, queryable but not indexed by default
    raw_ref: str                     # pointer into cold storage
    unmapped: dict[str, Any]        # fields we saw but have no canonical home for
```

Two design decisions worth flagging:

1. **`time_confidence` is a first-class field, not a warning log.** With monthly in-person cadence and remote sources, a forwarder with a wrong clock can poison a 24-hour detection window. Rather than rejecting skewed events, I mark them and let detections opt into strict or lenient time handling. Rejecting log data is almost always the wrong answer.
2. **`unmapped` exists on purpose.** When a new source field appears, it lands there rather than being dropped. A weekly job reports unmapped-field frequency, which becomes the backlog for adapter improvements. This is how normalization converges instead of rotting.

**Storage.** Hot tier in ClickHouse (or Timescale if the team prefers Postgres-adjacent ops) — partitioned by `toYYYYMMDD(occurred_at)`, ordered by `(tenant_id, source_type, occurred_at, event_id)`. Tenant first in the sort key because the overwhelmingly common query shape is tenant-scoped. Cold raw in object storage with a lifecycle policy; `raw_ref` resolves through a pre-signed URL issued by the API, never by direct bucket exposure.

**API design.** FastAPI (or Go/Chi if the team's runtime is Go — the contract is what matters, not the framework):

```
POST   /v1/events/search        # structured query, cursor pagination, no offset
GET    /v1/events/{event_id}    # single event + raw_ref pre-signed URL
GET    /v1/detections           # paginated detection catalog
POST   /v1/detections/{id}/test # dry-run a detection against a time range
POST   /v1/rules                # detection-as-code ingest from CI
GET    /healthz /readyz /metrics
```

Contract rules:

- **Cursor pagination only.** Offset pagination over a stream that's actively ingesting produces duplicate and skipped rows; that is unacceptable in an evidence-bearing system.
- **Every query carries an explicit tenant scope**, enforced at the repository layer, not by caller discipline. Cross-tenant reads are a security defect, and the only reliable defense is a query builder that cannot emit a tenant-less statement.
- **Time bounds are mandatory** on `/events/search`. Unbounded scans are the classic way a security analytics API takes down its own database.

### 2.3 Concurrency and consistency

- **Exactly-once end-to-end** via Kafka transactional producers + idempotent ClickHouse inserts keyed on `event_id` (ReplacingMergeTree with `event_id` in the sort key, so retries collapse rather than duplicate).
- **Optimistic concurrency on detection edits** — `ETag`/`If-Match` on rule updates. Two analysts editing the same rule during an incident is a real scenario, and last-write-wins silently destroys someone's work.
- **Advisory locks only for schema migration**, never for the query path. Long-held locks on a live telemetry store cause exactly the outage you're trying to detect.

### 2.4 Production readiness

- **CI/CD:** GitHub Actions. Stages — lint/type-check → unit → golden-file normalizer tests → integration against ephemeral Kafka + ClickHouse (Testcontainers) → schema-migration dry run → container scan (Trivy) → deploy. Detection rules are tested in the same pipeline; a rule that fires on the benign corpus fails the build.
- **Observability:** OpenTelemetry traces spanning ingest→normalize→persist with a propagated `event_id` as the correlation key — so "why didn't this alert fire" becomes a single trace query. Prometheus metrics: `ingest_events_total{source,status}`, `normalize_duration_seconds` (histogram), `unmapped_field_total{source,field}`, `query_p95_seconds{endpoint}`, `detection_evaluations_total{rule,result}`. Alerting on *pipeline silence* (`rate(ingest_events_total) == 0` for a source that normally reports) is as important as alerting on errors — an adversary's first move is often to stop the logs.
- **Load testing:** k6 or Locust against a synthetic corpus sized to 10x projected peak, with the specific adversarial shapes called out — high-cardinality dimension queries, bursty ingest during simulated incident storms, and cold-cache dashboard loads.
- **Zero-downtime deploys:** rolling with readiness gates; expand/contract schema migrations (add column → backfill → switch reads → drop old, never in one release); feature flags for detection changes so a bad rule can be disabled without a deploy.
