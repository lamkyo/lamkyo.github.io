## 2. Deep Technical Solution Blueprint

### 2.1 Architectural stance: the client is a replica, not a view

The single most expensive architectural mistake in production React Native is treating the app as a renderer over a live API. It works in the demo. It dies at scale, because:

- Cellular networks are intermittently connected, high-latency, and *lie about connectivity* (captive portals return 200 on a redirect).
- Every screen becomes a bespoke loading/error/retry state, which is 60% of the bug surface.
- Any mutation issued at 0% battery / airplane mode is lost, and users do not re-enter data.

**The stance:** the RN client owns a durable local replica. All reads hit a local store. All writes hit an **append-only outbox**. A background sync engine reconciles. The UI is a pure function of the replica state machine. This gives a single, testable convergence contract instead of per-screen improvisation.

```
┌──────────────────────────────────────────────────────────────┐
│                      React Native Client                     │
│                                                              │
│  UI (React) ──► Replica Store (DB/MMKV) ──► Sync Engine      │
│       ▲                │                        │            │
│       │         optimistic read          outbox append       │
│       └────────────────┘                        │            │
│                                                 ▼            │
│                                    ┌────────────────────┐    │
│                                    │  Outbox (durable)  │    │
│                                    │  per-entity FIFO   │    │
│                                    │  idempotency keys  │    │
│                                    └────────────────────┘    │
│                                                 │            │
│                              BGTaskScheduler / WorkManager   │
└─────────────────────────────────────────────────┼────────────┘
                                                  ▼
                        POST /v1/sync  (batched, If-Match, Idempotency-Key)
                        GET  /v1/sync?since=  (delta pull)
```

### 2.2 Core components

**A. Sync transport (API design)**

Two endpoints. That's it. Not one per resource.

- `POST /v1/sync` — accepts a batch of up to 100 mutations. Each carries `idempotencyKey` (client ULID, stable across retries) and `baseRevision`. Response is **per-item**, never all-or-nothing: `{ results: [{ id, status: 'applied' | 'conflict' | 'rejected', revision?, serverRecord?, error? }] }`. Partial failure is the norm; a batch that fails atomically forces the client to re-derive what succeeded.
- `GET /v1/sync?since=&limit=500` — delta pull with tombstones included. The cursor is server-opaque (a monotonic log offset), not a timestamp — timestamps are wrong under clock skew and backfill.

**Hardening details that matter in production:** `Idempotency-Key` response cache keyed by `(tenant, key)` with a 24h TTL so a retried batch after a timeout is a no-op; `ETag`/`If-Match` on single-record writes for optimistic concurrency; gzip/br on responses (mobile payloads are JSON-heavy); cursor-based pagination so a slow client can't force a full-table scan.
