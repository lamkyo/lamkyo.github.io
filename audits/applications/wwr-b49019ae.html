## 2. Deep Technical Solution Blueprint

### 2.1 Problem framing

Safety ML at Discord decomposes into three planes, each with different latency, recall, and explainability requirements:

| Plane | Examples | Latency | Decision mode |
|---|---|---|---|
| **Real-time content** | message text/image/attachment classification on send path | p99 ≤ 50ms added | inline allow/challenge/block |
| **Account integrity** | ban evasion, coordinated abuse, raid detection | seconds–minutes | risk score → step-up or enforcement |
| **Batch/platform** | server-level health, ring detection, retroactive sweeps | hours | async enforcement + analyst queues |

The architecture below is what I'd propose in Sprint 1 and what I'd expect to defend in a design review.

**Key design decisions I'd advocate:**

1. **Decision service is policy, not model.** Models emit calibrated scores + model version; a separate policy layer (versioned, auditable, hot-reloadable) maps scores → actions per surface and severity. This decouples model iteration from enforcement risk and gives Legal/Policy a reviewable artifact.
2. **Single decision log as the source of truth.** Every decision (score, features snapshot pointer, model version, policy version, action, outcome) is written to an append-only Kafka topic → Iceberg. This is what makes counterfactual evaluation, retroactive re-scoring ("what would the new model have done last month?"), and appeal/audit workflows possible.
3. **Feature store with point-in-time correctness.** Online store (Redis/Scylla) for serving; offline store (Iceberg) for training — with point-in-time joins so training never leaks future information. This is the single most common source of silent train/serve skew in abuse detection.
4. **Two-model pattern for content:** a cheap high-recall first pass (distilled transformer or linear-on-embeddings, runs on every message) gating a heavier high-precision second pass (multimodal LLM-classifier) on the ambiguous band. Keeps p99 budget while concentrating compute where it changes the decision.
5. **Graph signals computed async, consumed real-time.** Raid/ban-evasion rings are detected by streaming connected-component and graph-embedding jobs (Flink Gelly / custom); results land as features ("member_of_suspicious_ring:0.91") in the online store within seconds — never on the inline path.

### 2.3 API design (decision service)

```protobuf
service SafetyDecision {
  // Inline, p99 ≤ 25ms excluding model inference
  rpc ScoreMessage(ScoreMessageRequest) returns (ScoreMessageResponse);
  rpc ScoreAccount(ScoreAccountRequest) returns (ScoreAccountResponse);
  // Async, for analyst workflows and retroactive sweeps
  rpc BatchScore(BatchScoreRequest) returns (stream BatchScoreResponse);
}

message ScoreMessageResponse {
  string decision_id = 1;          // ties to decision log
  Verdict verdict = 2;             // ALLOW | CHALLENGE | BLOCK | QUEUE_FOR_REVIEW
  repeated ModelScore scores = 3;  // per-model, calibrated, with model_version
  map features = 4; // snapshot for explainability (sampled)
  PolicyVersion policy_version = 5;
}
```

**Contract rules:** idempotency keys on all mutations; decision_id is the correlation ID propagated through Kafka, traces, and analyst tooling; responses carry `Retry-After` semantics so gateway degrades to allow-with-logging (fail-open for availability) vs. fail-closed per surface — explicitly configured per surface, never defaulted.

### 2.4 Data modeling

- **Entities:** `user`, `message`, `attachment`, `server/guild`, `invite`, `device`, `payment_instrument` (hashed), `session`.
- **Behavioral features:** session-level sequences (action, target, delta-t) encoded via GRU/Transformer for account integrity; window aggregates (1h/24h/7d rates, unique-target counts, entropy of action targets).
- **Graph:** bipartite user↔guild and user↔user (mentions, co-joins, shared devices) edges in a streaming property graph; features = PageRank-ish centrality within suspicious subgraphs, ring membership, edge age.
- **Labels:** multi-source — automated enforcement outcomes (weak), T&S analyst judgments (strong), golden sets (curated, versioned, class-balanced), user appeals (adversarial, useful for FP analysis). Every label row carries `source`, `annotator`, `policy_version`, `timestamp` for label-quality monitoring.

### 2.5 Concurrency, caching, scalability

- **Serving:** stateless decision pods behind HPA; model servers (Triton) with dynamic batching; per-model autoscaling on queue depth, not just CPU.
- **Caching:** (a) feature cache in Redis with per-feature TTLs derived from feature freshness SLA; (b) decision cache keyed by `(content_hash, policy_version)` for duplicate/spam content — hit rates are high for coordinated abuse; (c) negative caching for known-clean senders' hot paths.
- **Concurrency control:** enforcement writes use optimistic concurrency with a per-user version vector (prevents race between a real-time block and a batch sweep); decision log writes are append-only (no contention).
- **Backpressure:** bounded queues in the gateway with explicit shed policy — shed to "score with cheap model" before shedding to "allow."
- **Scale targets I'd design for:** 10k+ msg/sec sustained, 3x burst; feature lookups p99 ≤ 3ms; full decision p99 ≤ 50ms; batch scoring of 200M+ accounts daily within a 4h window.

### 2.6 Production readiness

- **CI/CD:** GitHub Actions/Argo — lint → unit → data-contract tests → canary (1% traffic, auto-rollback on precision/recall guardrails) → progressive rollout. Model deployments use the same pipeline with **shadow mode** first (score, don't enforce) and **champion/challenger** traffic splitting.
- **Observability:** OpenTelemetry traces with `decision_id` propagation; Prometheus metrics per model (`score_distribution`, `feature_freshness`, `null_feature_rate`, `calibration_ece`, `pred_latency`); business dashboards (FP rate from appeals, enforcement precision by surface, label lag).
- **Drift & health:** PSI/KS on feature distributions, prediction-distribution drift, calibration drift, and **outcome-based recall proxies** (e.g., % of subsequently-confirmed-bad accounts that were scored high pre-enforcement). Alert on drift *and* on label-pipeline staleness — a silent labeling outage is the most dangerous failure mode in safety ML.
- **Load testing:** Locust/k6 replay of anonymized production traffic shapes; chaos tests for feature-store degradation (verify fail-open/fail-closed behavior per surface).
- **Zero-downtime:** blue/green model servers, feature store schema evolution via additive-only contracts, policy versions hot-reloadable without redeploy.
