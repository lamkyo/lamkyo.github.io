## 1. Executive Summary & Value Proposition

### The short version

AccuLynx is not a generic CRUD SaaS. It is an **operational system of record for a physical trade** — roofers, crews, adjusters, and homeowners coordinating around weather, insurance cycles, and trucks in driveways. That kind of product lives or dies on three hard engineering properties:

1. **Schedule integrity under concurrency.** Multiple dispatchers, office staff, and field crews touch the same job calendar simultaneously. Double-booked crews and lost appointments are not "bugs" to a roofing contractor — they are lost revenue and blown customer trust.
2. **Real-time state propagation.** A job status change in the office must be visible on a phone in a truck within seconds, on cellular networks, without hammering the origin database.
3. **Elastic query surfaces.** Contractors search across jobs, customers, documents, and estimates constantly. That is a text-search and geospatial problem, not a `LIKE '%...%'` problem.

My background is built around exactly these failure modes: transactional correctness in relational systems, cache coherence, event-driven projection pipelines, and API contracts that survive versioning and audit.

### On the AI-augmented engineering line item

AccuLynx explicitly asks for someone who *leverages* AI coding tools **and** who *actively evaluates and integrates* them across a team. That distinction matters, and I treat it as an engineering discipline rather than a novelty:

- **Where these tools genuinely win:** boilerplate DTO/mapper generation, test scaffolding, unfamiliar-library ramp-up, migrational transformations (e.g., converting a batch of NUnit tests to xUnit), regex and query translation, PR-description drafting.
- **Where they need guardrails:** anything touching concurrency, auth boundaries, money, or schema migrations. AI-generated `Task.Run` fire-and-forget, missing `ConfigureAwait` reasoning, unbounded `ToListAsync()` before filtering, and "helpful" retry loops that duplicate writes are the concrete failure patterns I review for.
- **How I'd institutionalize it:** a versioned `.github/copilot-instructions.md` encoding our architectural rules (repo patterns, no EF in controllers, required cancellation-token threading), a curated prompt library for recurring tasks, and a short "AI-assisted PR" checklist in the review template so quality standards stay explicit rather than assumed.

That is the difference between adopting a tool and operationalizing it — and it is the second thing the job description actually asks for.

## 2. Deep Technical Solution Blueprint

### 2.0 Reference architecture (logical)

```
                    ┌───────────────────────────────────────────┐
   Vue 3 SPA  ──────▶  ASP.NET Core Edge API (Minimal APIs)     │

                            │              │              │

                   │ Write Model   │ │ Cache      │ │ Read Model    │
                   │ SQL Server    │ │ Redis      │ │ ElasticSearch │
                   │ (ACID, rowver)│ │ (cache/lock│ │ (search/geo)  │
                   └────────┬──────┘ └────────────┘ └─────▲─────────┘
                            │                             │
                   ┌────────▼──────────┐          ┌───────┴──────────┐
                   │ Outbox (same txn) │◀─CDC────▶│ Projector Worker │
                   └────────┬──────────┘          └──────────────────┘
                            │
                   ┌────────▼──────────┐
                   │ SignalR Backplane │──▶ live push to subscribed clients
                   │ + Notification svc│
                   └───────────────────┘
```

The non-negotiable principle: **every state change is one ACID transaction in SQL Server that also writes its own event**, and every derived store (Redis, ElasticSearch, SignalR push) is a *projection* of that log. This is what guarantees the office app, the field app, and the API never disagree about whether a job is scheduled.

### 2.1 Public RESTful API design

Contract-first, generated from OpenAPI 3.1, with `.NET` Minimal APIs grouped by bounded context (`/v1/jobs`, `/v1/appointments`, `/v1/crews`, `/v1/materials`, `/v1/webhooks`).

Rules I'd enforce in review and in CI:

- **Versioning:** URL-major (`/v1`), additive within major. Breaking changes ship as `/v2` with a documented sunset header (`Sunset`, `Deprecation` per RFC 8594). No silent field removals.
- **Pagination:** cursor-based, never `OFFSET` on hot tables. Cursor is an opaque, HMAC-signed `(sortKey, id)`
