### 2.2 Integration principles

#### A. Use canonical contracts, not direct system coupling

Each integration flow should communicate through a stable business contract rather than exposing Salesforce or SAP structures throughout the platform.

For example:

```text
Canonical: Shipment
  shipmentId
  carrierCode
  serviceLevel
  originLocation
  destinationLocation
  plannedPickupAt
  plannedDeliveryAt
  trackingNumber
  status
  sourceSystem
  sourceVersion
  correlationId
```

Salesforce IDs, SAP customer numbers, carrier-specific status codes, and lake partitioning fields remain adapter concerns.

This prevents a Salesforce schema change from propagating into every downstream integration and makes it possible to replace a source system without redesigning the entire platform.

#### B. Separate synchronous commands from asynchronous facts

Not every integration should be implemented as a synchronous request/response call.

Use:

- **Synchronous APIs** for user-initiated queries and narrowly scoped commands where immediate confirmation is required.
- **Events** for state changes, completed business transactions, and data-lake ingestion.
- **Batch files** for legacy extraction, IDoc processing, scheduled reconciliation, and high-volume historical loads.

A typical command flow would be:

1. Receive an authenticated request.
2. Validate the payload against the versioned schema.
3. Assign a correlation ID and idempotency key.
4. Persist the command to a durable outbox.
5. Execute the orchestration through MuleSoft or a service adapter.
6. Publish success/failure state to an event stream.
7. Reconcile external acknowledgments and terminal state.
8. Alert on unresolved or partially completed transactions.

#### C. Make every write operation idempotent

External APIs and event streams can produce duplicates. Each operation should therefore have a stable idempotency key derived from:

```text
businessKey + operation + sourceVersion
```

Examples:

- Shipment creation: `SHIPMENT:{salesforceId}:CREATE`
- SAP material update: `MATERIAL:{sapMaterialId}:v{version}`
- Lake ingestion: `CARRIER:{carrierCode}:{fileName}:{fileHash}`

The idempotency record should contain:

- Key
- Request payload hash
- External operation identifier
- Processing state
- Timestamps
- Result reference
- Retry count
- Error classification

A repeated request with the same key and same payload should return the previous result. A repeated request with the same key and a different payload should be rejected as a conflict.

### 2.3 Salesforce integration design

Salesforce should be modeled according to the business capability, not merely by copying objects into another system.

#### Read paths

Use the appropriate Salesforce integration pattern:

- **REST API** for normal CRUD and focused queries.
- **Composite API** for related records and multiple operations.
- **Bulk API 2.0** for high-volume extraction.
- **Change Data Capture or Platform Events** for incremental change propagation.
- **External IDs and upsert semantics** for repeatable synchronization.

Salesforce API limits, governor limits, sharing rules, field permissions, and object-specific validation must be considered explicitly.

#### Write paths

For outbound writes:

- Use idempotent upsert operations where possible.
- Batch only when the downstream contract supports it.
- Treat partial batch success as a first-class outcome.
- Store Salesforce record IDs and API versions for traceability.
- Avoid retrying non-transient validation failures indefinitely.

#### Salesforce-specific controls

- Enforce least-privilege connected app permissions.
- Rotate credentials through the approved secrets manager.
- Separate integration users by function and environment.
- Monitor API consumption and daily limits.
- Use selective field retrieval rather than querying entire objects.
- Capture request IDs and correlation IDs for supportability.

### 2.4 SAP integration design

SAP integration requires explicit treatment of synchronous and asynchronous transaction semantics.

#### API/OData

Use OData for:

- Master-data reads
- Business-document queries
- Supported CRUD operations
- Metadata-driven synchronization

#### BAPI/RFC

Use BAPI or RFC for operations not exposed cleanly through OData, provided that:

- The business transaction is validated server-side.
- Return codes are interpreted as structured results.
- Commit or rollback behavior is explicit.
- Idempotency is enforced upstream.
- Sensitive configuration is stored outside source control.

#### IDoc

IDoc processing should be modeled as a durable batch workflow:

1. Receive or retrieve the IDoc.
2. Persist the raw payload.
3. Validate structure and business keys.
4. Deduplicate using document type, company code, document number, and version.
5. Transform into the canonical model.
6. Apply business validations.
7. Persist the result and acknowledgment.
8. Route errors to a replayable error queue.

The system must distinguish:

- Technical failure: safe to retry.
- Business validation failure: requires correction.
- Duplicate: acknowledge without reapplying.
- Partial failure: compensate, reconcile, or route to manual resolution.

### 2.5 Carrier data lake ingestion

The exact carrier data lake technology is not specified, so the design should remain infrastructure-neutral while enforcing the same operational properties.

#### Ingestion layers

```text
Raw landing zone
    ↓
Validated staging zone
    ↓
Deduplicated canonical records
    ↓
Curated/domain-ready tables
    ↓
Analytics and downstream consumers
```

#### Required controls

- Immutable raw retention for auditability.
- File checksum and source metadata.
- Schema validation before promotion.
- Reject records with invalid business keys.
- Deduplicate using event time, source version, and stable identifiers.
- Use partition keys based on access patterns, not arbitrary convenience.
- Track late-arriving and out-of-order data.
- Maintain lineage from carrier source to canonical record.
- Support replay from raw or validated staging layers.
- Quarantine malformed files without blocking valid batches.

For streaming ingestion, use:

- Durable event buffering.
- Consumer offsets or checkpoints.
- Schema compatibility checks.
- Dead-letter topics or queues.
- Exactly-once effects through idempotent processing rather than relying solely on transport guarantees.

### 2.6 Data Modeler and mapping governance

Mappings should be maintained as versioned, reviewable artifacts rather than embedded transformations.

Each mapping should define:

```text
Source system
Source object/entity
Source field
Canonical entity
Canonical field
Transformation
Validation rule
Direction
Handling strategy
Owner
Version
```

A mapping should distinguish:

- Direct mappings
- Default values
- Lookup mappings
- Conditional transformations
- One-to-many expansions
- Null and absent-value semantics
- Unit and timezone normalization
- Enum/code translation
- Data quality classifications

Example:

| Source | Source field | Canonical field | Rule |
|---|---|---|---|
| Salesforce | `Shipment__c` | `shipment.shipmentId` | Required; trim; preserve as string |
| Salesforce | `Carrier_Code__c` | `shipment.carrierCode` | Uppercase; validate against carrier registry |
| SAP IDoc | `VBELN` | `shipment.sapDeliveryNumber` | Preserve leading zeros |
| Carrier | `status_code` | `shipment.status` | Explicit code-map lookup |
| Carrier | `event_time` | `shipment.statusChangedAt` | Convert timezone to UTC |

Mapping changes should be versioned and tested against both valid and invalid fixtures.
