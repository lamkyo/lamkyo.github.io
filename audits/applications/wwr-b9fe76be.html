### Why this problem space specifically

Healthcare backends are hard for reasons that have nothing to do with CRUD. Three of them dominate:

1. **Correctness under concurrency is a clinical safety property.** Two clinicians editing the same encounter, or a booking engine double-allocating a slot, are not "eventually consistent" problems. They require explicit locking, optimistic versioning, and idempotent writes at the API boundary.
2. **Auditability is not optional and cannot be retrofitted.** Every read and write of a sensitive record must be attributable to an actor, a purpose, and a timestamp — stored append-only, outside the transactional blast radius of the primary tables.
3. **The regulatory frame constrains architecture.** In the Australian context, the *Privacy Act 1988* (APPs), the *My Health Records Act 2012*, and — where a provider is an NDIS participant's support — NDIS Practice Standards all impose retention, minimisation, access and breach-notification duties that translate directly into schema and API decisions. *(I would validate Yooli's exact obligations during discovery rather than assume them.)*

My proposal below is therefore not "a NestJS app." It is **an auditable, idempotent, horizontally-scalable REST/PostgreSQL core wrapped in a frontend that never holds more trust than it needs.**

## 2. Deep Technical Solution Blueprint

### 2.1 Architectural posture

**Modular monolith first, service extraction later — and only on evidence.**

A healthcare platform at Yooli's stage almost never benefits from premature microservices. The correct shape is a NestJS application partitioned into *bounded contexts* as modules with enforced boundaries (no cross-module imports except through exported façade providers), backed by a single PostgreSQL cluster using **schema-per-context** separation. This gives extraction optionality at near-zero cost while keeping distributed-transaction pain deferred until there is a real scaling reason to pay it.

├── src/
│   ├── main.ts                      # bootstrap, OTel init BEFORE Nest
│   ├── app.module.ts
│   ├── common/                      # cross-cutting: interceptors, guards, filters
│   │   ├── interceptors/{audit,tracing,idempotency,serialization}.ts

### 2.2 API design: REST as a contract

- **Versioning:** URI-versioned (`/api/v1/...`) plus `Sunset` / `Deprecation` headers on the previous version. Consumer-visible deprecation windows of ≥90 days, tracked in CI.
- **Resource semantics:** nouns, correct status codes (201 + `Location`, 409 for version conflict, 422 for semantic validation failure distinct from 400 syntax failure), `If-Match`/`ETag` for optimistic concurrency, `Idempotency-Key` for all non-idempotent POSTs.
- **Pagination:** **cursor (keyset) pagination only** on hot collections, never `OFFSET` — `OFFSET 20000 LIMIT 20` degrades linearly and produces phantom/skipped rows under concurrent inserts. Cursor is an opaque, signed base64 of `(sort_key, id)`.
- **Errors:** RFC 9457 `application/problem+json` throughout, with a stable machine-readable `type` and a `correlationId`. No stack traces, no ORM errors, ever, in a response body.
- **Contract-first:** `@nestjs/swagger` decorators emit OpenAPI 3.1 at build time; the frontend client is generated from that artifact in CI. A breaking schema change fails the frontend build — drift becomes impossible
