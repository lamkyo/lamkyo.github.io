## 2. Deep Technical Solution Blueprint

### 2.1 Problem framing

Pinterest's media surface is a **mixed image/video feed** served to hundreds of millions of monthly active users across heterogeneous devices and networks. The core tensions:

| Tension | Example |
|---|---|
| Quality vs. bytes | AVIF/HEVC compress better but cost encode time and device decode capability |
| Latency vs. smoothness | Prefetching more improves scroll smoothness but wastes bandwidth |
| Client autonomy vs. server control | Client-side ladder selection reacts faster; server-side is more consistent |
| Innovation vs. compatibility | New formats (AVIF, HDR10) need graceful fallback chains |

### 2.2 Proposed architecture: **Unified Media Delivery Plane (UMDP)**


**Key design decisions:**

1. **Variant Selector (control plane)** decides *which rendition* of a media asset a given client should fetch, using: device capability profile (codec support, screen size, HDR, memory class), network class (estimated throughput, RTT), product context (feed vs. detail vs. board cover), and A/B experiment assignment. This is a stateless, horizontally scalable service.

2. **Signed variant manifests** — the client receives a short-lived signed manifest listing candidate renditions + URLs. This keeps URL construction logic server-side (evolvable without app release) while letting the client adapt in real time within the allowed set.

3. **Client Adaptive Controller** does per-session adaptation (like ABR in HLS/DASH) using throughput EWMA + buffer health, with hysteresis to avoid oscillation.

4. **Prefetch Scheduler** is the scroll-smoothness lever: a priority queue driven by viewport prediction (velocity + direction), with a byte budget per network class and cancellation on scroll reversal.

**Design notes:**
- **Batch endpoint** — feed prefetch resolves N pins in one RTT.
- **Manifest signature** — prevents client-side URL tampering and allows CDN auth.
- **TTL + client cache** — manifest cached locally; re-resolve on TTL expiry or network-class change.
- **Graceful degradation** — if `preferred_fmt` unsupported, client walks `srcset` in order.

### 2.4 Data modeling

```
MediaAsset (immutable content record)
  asset_id            PK (string, "pin:")
  content_hash        blake3 of canonical bytes
  kind                ENUM(image, video, gif)
  source_width/height int
  duration_ms         int NULL (video)
  has_alpha           bool
  hdr                 bool
  created_at          ts

Rendition (derived, many per asset)
  rendition_id        PK
  asset_id            FK → MediaAsset
  kind                ENUM(image, video_segment)
  codec               string ("av1","hevc","h264","vp9","jpeg","webp","avif")
  width, height       int
  bitrate_kbps        int NULL (video)
  byte_size           int
  segment_idx         int NULL (video, for segmented delivery)
  storage_key         string (object store path)
  etag                string
  UNIQUE(asset_id, codec, width, height, segment_idx)

DeviceCapabilityProfile (client-reported, versioned)
  platform, os_major, codec_caps[], hdr, memory_class, screen_bucket
  → default ladder + format preference

DeliveryEvent (telemetry, append-only → columnar)
  event_id, asset_id, rendition_id, session_id, surface
  ts, client_ts, network_class, event_type
  (resolve|prefetch_start|fetch_start|first_byte|decode_start|first_frame|
   frame_drop|stall_start|stall_end|complete|error)
  bytes_served, ttfb_ms, decode_ms, dropped_frames
```

**Concurrency control:**
- Rendition generation is **idempotent per (asset_id, codec, w, h)** — a distributed lock (Redis `SET NX PX`) guards against duplicate encodes when multiple requests race for the same asset.
- Telemetry ingestion is append-only with **at-least-once** delivery; downstream aggregation is idempotent on `(event_id)`.

### 2.5 Caching strategy (multi-layer)

| Layer | What | Key | TTL / Invalidation |
|---|---|---|---|
| Client memory | decoded bitmaps (LRU) | asset_id + rendition_id | memory-pressure aware, size-capped |
| Client disk | encoded bytes | content_hash + rendition | LRU, size-capped (e.g. 256MB) |
| CDN edge | rendition bytes | storage_key | `Cache-Control: public, max-age=31536000, immutable` (content-addressed) |
| CDN edge | variant manifest | asset_id + device bucket | short TTL (300s) + signature |
| Service (Redis) | resolve response | asset_id + capability hash | 60s, invalidated on new rendition publish |
| Origin | transcode results | — | write-through on publish |

**Content-addressed storage** makes rendition URLs immutable → CDN cache hit rate stays high and invalidation is a non-issue for bytes; only manifests need short TTLs.

### 2.6 Scalability guarantees

- **Resolve service**: stateless, horizontal autoscale on CPU + p99 latency SLO. Target: p99 < 40ms at 50k RPS per region.
- **Fan-out**: batch resolve (≤100 assets) reduces RTTs; response compressed (gzip/br).
- **Transcode farm**: queue-backed (Kafka/SQS) with priority lanes — new pins > backfill > experimental formats. Backpressure via queue depth autoscaling.
- **CDN**: multi-CDN with health-based steering; per-region cache fill rate monitored.
