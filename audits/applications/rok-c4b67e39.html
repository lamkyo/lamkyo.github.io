          |                |
          v                v
   Background Workers   External Systems
   Notifications       Payments, email,
   CEU, reporting      video, webhooks

### Key design principles

- Keep business rules in application/domain services rather than controllers.
- Use explicit data-transfer objects and API contracts.
- Keep database transactions short and narrowly scoped.
- Use an outbox pattern where a business transaction must reliably trigger asynchronous work.
- Make external integrations idempotent and retryable.
- Avoid distributed transactions unless the business requirement and operational risk justify them.
- Use optimistic concurrency for frequently edited records and explicit isolation or locking only where required.
- Standardize telemetry around request, tenant, user, correlation, and operation dimensions.
- Keep secrets outside source control and configuration files.
- Build administrative workflows with auditable state transitions.

## 2.3 API design

For public or internal APIs, I would establish a consistent contract around:

- Resource-oriented URLs.
- Pagination and bounded page sizes.
- Standardized validation errors.
- Correlation IDs and trace propagation.
- Consistent date/time and timezone handling.
- Idempotency keys for commands that create financial or operational state.
- Idempotent payment and registration operations.
- Explicit authorization boundaries.
- API versioning where existing clients cannot safely migrate atomically.
- Stable error codes suitable for client automation.

Example error contract:

```json
{
  "error": {
    "code": "registration.capacity_reached",
    "message": "The event does not have sufficient remaining capacity.",
    "correlationId": "00-abcd1234-ef567890-1234-567890abcdef",
    "details": {
      "eventId": "5e2d8b20-0ad4-4a2a-8b0b-84d9c1cf9c8d"
    }
  }
}
```

I would avoid returning stack traces, database details, or internal exception messages to clients. Internal failures would be correlated through telemetry and structured logging.

### Critical command design

Commands such as the following should be designed as safely repeatable operations:

- Create registration.
- Capture payment.
- Issue refund.
- Transfer ticket.
- Publish event content.
- Enroll learner in a course.
- Record CEU completion.
- Send scheduled notifications.
- Synchronize sponsor or attendee data.

The API should persist an idempotency record within the same transaction as the business operation. A repeated request with the same key should return the original result or a well-defined “already processed” response.

## 2.4 SQL Server and data modeling

I would optimize the data model around the business lifecycle of an event and its related operations.

### Example aggregate boundaries

- Event
- Session
- Venue
- Registration
- Attendee
- Ticket type
- Order
- Payment
- Refund
- Sponsor
- Sponsor package
- Content item
- Course
- Enrollment
- CEU record
- Notification
- Audit record

### Design guidelines

- Use stable, non-sequential public identifiers where appropriate.
- Separate monetary values into `decimal`, never floating-point types.
- Store timestamps in UTC and preserve the original business timezone where event scheduling requires it.
- Use explicit enum-like status values with transition rules.
- Apply unique constraints that match actual business invariants.
- Use filtered indexes for common active-state queries.
- Index foreign keys and frequently used filter/order columns.
- Avoid unbounded queries and accidental full-table scans.
- Analyze execution plans before introducing broad indexing changes.
- Use query pagination consistently.
- Introduce read models or reporting replicas only after measuring a concrete need.
- Maintain a query-performance budget for high-volume endpoints.

### Concurrency control

I would use a combination of strategies based on the operation.

#### Optimistic concurrency

For records such as event details or sponsor profiles:

- Add a `rowversion` column.
- Include the expected version in update commands.
- Return a conflict when the version has changed.
- Allow the client to refresh and resubmit where appropriate.

#### Transactional capacity enforcement

For ticket registration, a naïve check followed by an insert can overbook an event under concurrent requests. The capacity check and reservation must occur inside a suitable transaction, with an appropriate isolation strategy or a database-enforced conditional update.

For example:

```sql
UPDATE dbo.EventInventory
SET ReservedCount = ReservedCount + @RequestedQuantity
WHERE EventId = @EventId
  AND ReservedCount + @RequestedQuantity <= Capacity;
```

A zero-row update would indicate insufficient inventory. The registration and payment state would then be handled using an explicit state machine rather than a single overloaded status.

#### Serialized state transitions

For payments, refunds, CEU completion, and external synchronization, I would use controlled state transitions:

```text
Pending -> Processing -> Succeeded
Pending -> Processing -> Failed
Succeeded -> RefundPending -> Refunded
Failed -> RetryableFailure
```

Transitions would be validated in the domain layer and persisted transactionally.
