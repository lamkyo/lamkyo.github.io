## 2. Deep Technical Solution Blueprint

Because Lemon.io matches engineers to *many* client systems, I'll anchor the blueprint in a domain I can reason about concretely: **the matching and contracting core of a two-sided talent marketplace** — your own domain — and note where it generalises to the typical client engagement.

### 2.1 Architectural stance

- **Modular monolith** (single ASP.NET Core host) with **vertical slice** organisation: `Features/Match/`, `Features/Contract/`, `Features/Payout/`, each owning its own endpoints, handlers, and EF configuration. Boundaries enforced by an architecture test (NetArchTest) that fails CI if `Payout` references `Match` internals.
- **CQRS-lite, not CQRS-ceremony.** Commands go through EF Core aggregates in a transaction; reads go through projection queries (`AsNoTracking`, `Select` straight to DTOs) and, where p95 demands it, through Redis-cached read models. No event sourcing unless the client's audit requirements actually demand it.
- **Async work through an outbox**, never fire-and-forget `Task.Run`. Domain events are written in the same transaction as the state change, then relayed to Azure Service Bus.
- **Everything is a capability, not a service.** Search, scoring, notifications, and webhooks are separate *workers* in the same solution, independently scalable, sharing the domain project.

### 2.2 API design

- **Minimal APIs** grouped by slice, with `TypedResults`, endpoint filters for validation, and OpenAPI generated at build.
- **Contracts:** request/response DTOs are versioned (`v1`) and additive-only. `ProblemDetails` (RFC 9457) for every failure, with a stable machine-readable `type` URI — clients branch on `type`, never on message text.
- **Idempotency:** every mutating POST accepts `Idempotency-Key`. Middleware stores `(key, tenant, requestHash) → response` in SQL with a 24h TTL; replay returns byte-identical response, mismatched body returns `422`.
- **Pagination:** opaque cursor (`created_at, id` keyset), never `OFFSET`. Stable under concurrent inserts — critical for a feed a founder scrolls while matching runs.
- **Rate limiting:** `AddRateLimiter` with a partitioned sliding window keyed on API key + tenant, returning `Retry-After`.
- **Client generation:** Kiota or `openapi-typescript` produces the TS client in CI, so frontend/backend drift is a compile error, not a bug report.

### 2.3 Data modelling

- **Azure SQL + EF Core 9** (PostgreSQL is a drop-in preference when the client's team already runs it — I have no religious attachment).
- **Append-only truth for money.** `ledger_entries` is insert-only, double-entry, with `debit_account`, `credit_account`, `amount_minor` (integer minor units — never floats for currency), `currency`, `occurred_at`. Balances are derived, cached, and reconciled nightly. Corrections are new compensating entries.
- **Reference data vs. transactional data split:** developer profiles, skills, and client requirements are read-heavy and cached; contracts and ledger are write-heavy and never cached beyond a single request.
- **Temporal history** (`TemporalTable`/`SYSTEM_VERSIONING`) on `contracts` and `developer_profiles` so "what did the offer look like when they accepted it" is answerable without a bespoke audit table.
- **Indexes designed from queries**, not from entities: covering indexes on `(tenant_id, status, created_at DESC)` for work queues; filtered indexes for the small hot subsets (`WHERE status = 'Pending'`).
