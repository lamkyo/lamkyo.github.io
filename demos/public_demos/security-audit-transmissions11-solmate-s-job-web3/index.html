Critical Vulnerability

[H-01] Missing Check for Contract Existence

SafeTransferLib.safeTransfer and safeTransferFrom Leading to False Positives on Non-Existent Tokens

Severity High
Vulnerability Type Logic Error / External Call
Code Location SafeTransferLib.sol
Impact Silent Fund Loss / Bypass

Vulnerability Description & Root Cause

Contracts relying on SafeTransferLib.safeTransfer or safeTransferFrom to interact with non-existent or self-destructed tokens will assume successful token transfers when no actual transfer occurs, potentially allowing users to bypass payment requirements or accounting checks.

// Vulnerable assembly snippet in src/utils/SafeTransferLib.sol
if and(iszero(and(eq(mload(0), 1), gt(returndatasize(), 31))), success) {
    success := iszero(or(iszero(extcodesize(token)), returndatasize()))
}

If an address with zero code size (extcodesize == 0) is passed as a token, and it returns no data (returndatasize == 0), the assembly evaluates: iszero(or(iszero(0), 0)) -> iszero(0) -> 1 (true).

Proof of Concept (Foundry / Forge) 

contract SafeTransferBypassTest is Test {
    using SafeTransferLib for ERC20;

    function testBypassNonExistentTokenTransfer() public {
        // Address with no code (EOA or self-destructed contract)
        address fakeToken = address(0xDEADBEEF);
        
        // This call will not revert because extcodesize is 0 and returndatasize is 0,
        // causing Solmate to consider it a successful "no return data" token.
        SafeTransferLib.safeTransfer(ERC20(fakeToken), msg.sender, 100e18);
    }
}

Recommended Remediation

Explicitly check that extcodesize(token) > 0 before treating zero return data as a valid ERC20 transfer, or enforce that the target has contract bytecode:

if and(iszero(and(eq(mload(0), 1), gt(returndatasize(), 31))), success) {
    success := and(gt(extcodesize(token), 0), iszero(returndatasize()))
}
