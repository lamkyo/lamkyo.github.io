Executive Hook — The Diagnostic Most Bidders Miss You are not asking for "an app that draws stitches." You are asking for a **digitizing engine with a UI bolted on top** — and the failure mode of 90% of embroidery software projects is that the team builds the UI first, treats the stitch engine as a black box, and discovers on delivery day that the exported file won't run on the client's machine. Here is what your brief actually implies, and where the subtle traps live: **The real problem is not pattern creation. It is stitch-path correctness.** An "intricate embroidery pattern" is a geometric path plus a **stitch-type decision** (satin, fill, running, motif) plus **underlay** plus **pull compensation**. Intermediate users will judge your software on one thing: *does the exported design sew out without puckering, gaps, or thread breaks?* A beautiful canvas that produces a bad `.DST` is worthless. **The traps that sink this class of project:** | Trap | Why it kills the project | Our mitigation | |---|---|---| | **File-format endianness & header checksums** | Tajima `.DST`, Melco `.EXP`, and Barudan `.DSB` encode stitch deltas in signed 3-byte little-endian with format-specific terminators. A single off-by-one byte produces a file that opens in the editor and fails on the machine. | Byte-exact round-trip tests against known-good reference files before any UI work. | | **Coordinate space confusion** | Design space (mm), stitch space (0.1 mm units), and screen space (px) get conflated. Zoom/pan then silently corrupts exported geometry. | Single canonical internal unit (0.1 mm integer), explicit conversion boundary, property-based tests. | | **Pull compensation & underlay treated as "polish"** | They are not. Without them, satin columns gap and fills pucker. Retrofitting them means rewriting the stitch generator. | Compensation and underlay are first-class parameters in the Phase 2 data model, not a later patch. | | **Thread-color / palette model** | Intermediate users expect a thread chart (Madeira/Isacord-style) with per-block color assignment, not raw RGB. | Palette abstraction from day one; export maps to nearest machine-legal color index. | | **Windows-only rendering assumptions** | GDI+ vs. Direct2D vs. SkiaSharp changes hit-testing, DPI scaling, and print fidelity. | Rendering layer isolated behind an interface so the backend is testable headless. | **The strategic point:** the £5,000–£10,000 range is a *product* budget. Regression Guardrails Zero-regression is an engineering discipline, not a promise. Our guardrails: 1. **Golden corpus as contract.** The reference embroidery files are committed to the repo. Any change that alters their round-trip output fails CI immediately. 2. **Byte-exact export tests.** Exporters are tested against frozen expected outputs. No "close enough." 3. **Property-based invariants.** Geometry and stitch invariants are asserted across thousands of generated inputs per run — catching regressions that hand-written tests miss. 4. **Snapshot rendering.** Deterministic rasterization compared per-commit; visual regressions surface as diffs. 5. **Fuzz regression suite.** Every malformed input that ever caused a crash becomes a permanent test case. 6. **CI gate.** No merge without green tests. Branch protection enforced. 7. **Semantic versioning of the format layer.** Any change to export behavior is a versioned, documented event — never a silent edit. 8. **Isolated engine.** Because the engine is UI-agnostic and headless-testable, UI changes cannot regress stitch correctness, and vice versa. --- ## 5.
