1. Executive Hook — What You Actually Need (And What Most Bidders Will Miss)

You asked for a platform that "watches Binance, Coinbase, Kraken and more simultaneously." That sentence hides the entire difficulty of this project. The hard part is not connecting to exchanges — every bidder will show you a WebSocket demo that ticks a price. The hard part is the three problems nobody puts in their proposal:

Pitfall #1 — The "and more" trap. A naive build hardcodes three exchange integrations. The moment you want a fourth, you pay for a rewrite. The correct architecture is an exchange adapter abstraction: a single normalized internal schema (order book, trades, volume, open interest) that every venue maps into. Adding an exchange becomes a config file, not a sprint.

Pitfall #2 — Order-book integrity. Live order books are not "a list of prices." They are a sequenced delta stream that must be reconstructed against a REST snapshot with strict sequence-gap detection. Miss a sequence number and your book silently corrupts — you'll see phantom liquidity and make decisions on data that never existed. Most bidders ship a UI that *looks* live but is quietly wrong. We treat gap detection and resync as a first-class feature, not an afterthought.

Pitfall #3 — Rate limits, reconnects, and clock skew. Exchanges throttle, disconnect, and drift. A production monitor needs exponential backoff, heartbeat monitoring, and per-venue rate-limit budgeting — otherwise your dashboard freezes at the exact moment volatility spikes, which is the only moment you care about.

The real deliverable is trust. You are not buying a dashboard. You are buying a system whose numbers you can act on. Every architectural decision below serves that single goal.

2. Architecture & Technical Plan

High-Level Topology

``` [ Binance WS ]──┐ [ Coinbase WS ]─┤──► [ Ingestion Workers ] ──► [ Normalizer ] ──► [ Redis Streams ] [ Kraken WS ]───┤ (per-venue) (unified schema) │ [ +N adapters ]─┘ ▼ [ Aggregation Engine ] (volume, OI, spread, depth) │ ▼ [ WebSocket Gateway ] ──► [ Browser UI ] (auth-gated, throttled) (live charts) ```

Stack: Node.js/TypeScript ingestion workers (native WS performance, shared types with frontend), Redis Streams as the internal bus, PostgreSQL for historical snapshots, a React + lightweight-charts frontend, all orchestrated with Docker Compose. PHP is available for any legacy integration you already run — the gateway exposes a clean REST/WS contract either way.

Phase 1 — Isolation, Discovery & Reproduction (Day 1)

- Environment isolation: dedicated Docker network; no shared state with any existing system you run. Your current tooling is untouched. - Discovery: confirm which venues, which instruments, which metrics (volume, open interest, funding, spread, depth) matter most, and your latency tolerance. - Baseline reproduction: stand up the three primary adapters (Binance, Coinbase, Kraken), capture a raw message sample from each, and document the exact schema differences. This becomes the contract every future adapter must satisfy. - Deliverable at end of Day 1: a running ingestion skeleton streaming real data into Redis, plus a written adapter spec.

Phase 2 — Implementation & Automated Verification (Day 2–3)

- Normalizer: unified schema across all venues — `{venue, symbol, bids[], asks[], last, volume, openInterest, ts}`. - Order-book reconstruction: snapshot + delta replay with sequence-gap detection and automatic resync. - Aggregation engine: rolling volume, open-interest tracking, spread and depth metrics, cross-venue comparison. - Auth-gated WebSocket gateway: secure login, per-session throttling, backpressure handling so a slow client never stalls ingestion. - Frontend: live order-book ladder, multi-venue price overlay, volume/OI charts, venue health indicators. - Automated tests: unit tests for the normalizer and book reconstruction; integration tests replaying recorded exchange fixtures (including a deliberately corrupted sequence stream to prove resync works).

Phase 3 — Hardening, Performance & Handover (Day 3–4)

- Resilience: exponential backoff, heartbeat/liveness monitoring, per-venue rate-limit budgeting, graceful degradation when one venue drops. - Performance: latency profiling end-to-end (exchange timestamp → browser paint), memory-leak checks on long-running streams, load test with simulated client fan-out. - Security pass: credential handling via environment secrets, TLS, input validation on the gateway, no exchange keys ever exposed to the browser. - Handover: architecture doc, runbook, adapter-authoring guide, and a recorded walkthrough.

4. Regression Guardrails

Zero-regression is a design constraint, not a promise:

1. Full isolation. The entire system runs in its own Docker network. Nothing touches your existing services, databases, or credentials. 2. Fixture-based integration tests. Every adapter is tested against recorded real exchange messages. If a change breaks parsing, the test fails before it reaches you. 3. Corrupted-stream test. A dedicated test feeds a deliberately broken sequence stream and asserts the system detects the gap and resyncs — proving the integrity guarantee holds under failure. 4. Contract tests on the normalized schema. Any adapter that violates the unified schema fails CI. This is what makes "and more" exchanges safe to add later. 5. CI gate. No merge without green tests. You get the pipeline config, so you can verify this yourself. 6. Versioned releases. Each phase is tagged, so any regression can be bisected to a single commit.
