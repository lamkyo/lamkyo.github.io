Executive Technical Hook **The core pain point:** translating collected market data into alerts sounds trivial — "fire when price crosses X" — but in practice, threshold alerting on live market data fails along four predictable axes: | Failure Mode | Root Cause | Consequence | |---|---|---| | **Duplicate / alert storms** | No state tracking between evaluations | Inbox flooded, alerts ignored | | **Stale or delayed triggers** | Polling cadence mismatched to data freshness | Signal arrives after the move | | **Silent gaps** | No observability on the evaluation loop | You don't know an alert *didn't* fire | | **Brittle thresholds** | Logic hard-coded per alert | Every new alert = new code | The Deep Pattern Builder is the right surface for this — it's designed to express pattern conditions declaratively. The engineering discipline is in making the *evaluation* deterministic and the *state transitions* explicit, so a threshold crossing is a well-defined event rather than an emergent side effect. **My design principle:** *an alert is a state machine, not a comparison.* A crossing is a transition (below → above), and only a genuine transition should notify. This single insight eliminates the majority of real-world alerting defects. --- ## 2. Returns (signal_or_none, new_state). A signal is emitted ONLY on a genuine state transition. """ is_breached = (value > threshold) if direction is Direction.ABOVE else (value < threshold) # First observation: establish baseline, do not fire. if prev_state is None: return None, is_breached # Edge trigger: fire only on transition into breached state. if is_breached and not prev_state: return Signal(symbol, condition_id, value, threshold, direction, timestamp), is_breached return None, is_breached ``` **Test coverage (Phase 1):** - Unit tests for `evaluate`: first-observation baseline, edge trigger, no re-fire while breached, re-arm after recovery, boundary equality (`value == threshold`). - Integration test: synthetic series → expected signal sequence. - Idempotency test: replaying the same series produces identical signals. ### Phase 2 — Hardening, Observability & Multi-Alert Scale - **Idempotency & dedup:** Signal keys are deterministic (`symbol:condition:transition_ts`), so retries and replays never double-notify. - **Observability:** Structured logging on every evaluation cycle + a heartbeat metric. *Silence is ambiguous* — you must be able to distinguish "no crossing" from "evaluator stopped." - **Config-driven alerts:** Thresholds, directions, and symbols move to declarative config (YAML/JSON), so adding alert #2 through #N is a config edit, not a code change. - **Backpressure & rate limiting:** Coalescing window so a volatile symbol can't flood notifications. - **Security:** Secrets (webhook URLs, API keys) via environment/secret store — never in code or config committed to VCS.
