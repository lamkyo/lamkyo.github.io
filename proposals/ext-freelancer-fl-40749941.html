Executive Technical Hook Every third-person combat prototype I've been handed has the same three failure modes: **Animation vs. locomotion fighting.** Root-motion clips and a `CharacterController` both want authority over translation. The result is jitter, sliding feet, and attacks that teleport the player. Fix: single source of truth — code-driven locomotion with root motion as *authoring reference only*, reconciled in `LateUpdate` with a deterministic motion-warp blend. **Combats that feel dead.** No hit-stop, no input buffering, no cancel windows. The player presses attack, the game queues nothing, and a 200 ms input lands after the montage ends — read as "unresponsive." Fix: an explicit attack state machine with startup/active/recovery frames, a 150 ms input buffer, and a configurable cancel table. **Homogeneous enemies.** Robots, bugs, and humans all get the same walk-to-player-and-swing loop, so the game reads as one enemy with three skins. Fix: a shared `IEnemyBrain` contract with archetype-specific behaviour modules — bugs get flocking and overwhelm, humans get cover and flanking, robots get telegraphed heavy attacks and weak points. I build for those failure modes first. The visual polish is downstream and cheap once the systems are correct. ## 2.
