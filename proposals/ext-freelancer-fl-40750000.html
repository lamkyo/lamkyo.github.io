Executive Technical Hook The core pain point isn't administrative bandwidth — it's **the absence of a durable process artifact**. Three symptoms follow from it: - **Onboarding** is re-derived per hire, so quality varies with whoever is available that week. - **Induction** is content without state: no record of who has completed what, no audit trail, no way to prove compliance. - **Training coordination** is a calendar problem masquerading as a people problem — it needs scheduling, reminders, and completion tracking, not more meetings. The correct engineering response is a **single source of truth with role-scoped views**: one schema for people, tracks, modules, and completion events; three interfaces (admin, manager, new hire) over the same data. That eliminates the drift between what's documented and what's actually happening. ## 2. Architecture & Technical Plan **Stack:** PHP 8.x (PDO, prepared statements throughout), MySQL/MariaDB, semantic HTML5, hand-written CSS (no framework dependency), vanilla JS for progressive enhancement. Deployable on standard shared hosting — no build pipeline required, because your future admin shouldn't need one. ### Phase 1 — Data Model & Onboarding Core (Days 1–3) Normalized schema, designed before a single template is written: ``` employees (id, name, email, role_id, start_date, status) tracks (id, name, role_id, description, active) modules (id, track_id, title, type, content_ref, sort_order, required) completions (id, employee_id, module_id, completed_at, verified_by) training_events(id, title, scheduled_at, capacity, owner_id) enrollments (id, event_id, employee_id, status, reminder_sent_at) ``` Design decisions that matter: - **`completions` is append-only.** Completion is an event, not a boolean. You get a full audit trail for free, and "who signed off on this" is always answerable. - **Tracks are role-scoped.** A new engineer and a new salesperson get different induction paths from the same engine. - **Soft deletes on `tracks` and `modules`.** Retiring a module must never orphan historical completion records. Deliverable: schema, migrations, seed data, and a working admin CRUD for tracks and modules. ### Phase 2 — Induction Workflow & Training Coordination (Days 4–7) - **New-hire view:** their assigned track, module-by-module progress, next action surfaced at the top. - **Manager view:** team completion dashboard, overdue items flagged, one-click verification. - **Training calendar:** event creation, capacity limits, enrollment, and automated reminder dispatch via cron. - **Notification layer:** email on assignment, on overdue threshold, and on completion — templated, not hardcoded. ### Phase 3 — Hardening, Handover & Documentation (Days 8–10) - **Security:** CSRF tokens on every mutating request, `password_hash()`/`password_verify()` for auth, output escaping via `htmlspecialchars()` at every render point, strict session handling, least-privilege DB user. No raw SQL string interpolation anywhere in the codebase. - **Test coverage:** PHPUnit suite covering the completion state machine, role-based access boundaries, and reminder scheduling logic. Target: every branch in the authorization layer exercised. - **Zero regression:** all schema changes delivered as forward-only migrations; no destructive alters; existing data preserved on every deploy. ## 3.
