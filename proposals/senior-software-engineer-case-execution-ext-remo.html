A deliverable without automated tests and a reproducible run command is a liability, not an asset.

My approach inverts all four. I isolate, reproduce, fix, and prove — then hand you a repo that runs green on your machine in one command.

2. Architecture & Technical Plan

Phase 1 — Isolation, Discovery & Reproduction (Day 1)

Objective: Eliminate ambiguity. Convert the case brief into a deterministic, testable specification.

- Codebase Reconnaissance: Map the relevant module boundaries, data models, and existing test infrastructure. Identify the exact entry points the case touches. - Domain Contract Extraction: Document the implicit contracts — input schemas, expected outputs, error semantics, and any payer/IDR-specific business rules embedded in the code. - Reproduction Harness: Write a failing test first (red) that captures the requirement or defect precisely. This becomes the objective definition of "done." - Risk Register: Flag any hidden coupling, non-determinism, external dependencies, or data assumptions that could cause the fix to pass locally but fail in CI or production. - Deliverable at end of Day 1: A short written Discovery Note + the failing reproduction test, committed to a branch.

Phase 2 — Implementation & Automated Verification (Day 2–3)

Objective: Ship the smallest correct change that satisfies the spec — no scope creep, no collateral damage.

- Minimal-Surface Implementation: Change only what the requirement demands. Prefer extending existing patterns over introducing new abstractions. - Correctness-First Coding Standards: - Currency handled as integer minor units or `Decimal` — never floats. - Any submission/retry path made idempotent (idempotency keys or equivalent). - All state transitions logged and auditable. - Timezone-aware date handling for any deadline/filing logic. - Test Pyramid: - Unit tests for the core logic (happy path + boundary + error cases). - Integration test proving the change works against the real module boundary. - The Phase 1 reproduction test now passes (red → green). - Daily Written Standup: What shipped, what's next, any blockers — async, timestamped.

Phase 3 — Hardening, Performance & Handover (Day 3–4)

Objective: Make the change production-safe and hand it over so anyone on your team can run, verify, and extend it.

- Edge-Case Hardening: Null/empty inputs, malformed payloads, concurrent access, retry storms, and boundary values. - Performance Sanity Check: Confirm no N+1 queries, no accidental O(n²) loops, no unbounded memory growth introduced by the change. - Regression Sweep: Run the full existing test suite — not just the new tests — and report the before/after pass counts. - Handover Package: README with exact run/verify commands, a diff summary, and a short "what I'd do next" note for follow-on work.

Minimal-Surface Principle: The blast radius of every change is deliberately minimized — no opportunistic refactors, no drive-by formatting, no dependency bumps. 4.
