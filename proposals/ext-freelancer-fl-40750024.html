# Technical Proposal & Cover Letter **Project:** Logistics Software & Android App (Full Truck Load Operations) **Client:** Small logistics firm — 3 internal users **Budget:** ₹600 – ₹1500 INR --- ## Cover Letter Dear Client, You run full truck loads — not parcels, not multi-drop LTL. That single fact changes everything about how this software should be built, and it's the first thing most developers bidding on this job will get wrong. FTL logistics lives and dies on **trip-level state**, not shipment-level state. One truck, one origin, one destination, one consignment, one freight bill. There is no bin-packing, no route optimization across hundreds of stops, no warehouse scan-in/scan-out. What you actually need is a **lean, auditable order lifecycle** — booked → dispatched → in-transit → delivered → POD collected → invoiced — with a clean Android client for your drivers or field staff to update status from the road, and a web/PHP backend that your three office users can trust as the single source of truth. With only three users, you do **not** need a bloated ERP. You need something that works on day one, doesn't break on day ninety, and costs you nothing to maintain. That is exactly what I build. I'd like to walk you through the plan below. --- ## 1. Executive Technical Hook — The FTL Pain Point The core failure mode in small FTL operations is **status drift**: the office thinks a truck is in-transit, the driver delivered yesterday, and the POD is still in a WhatsApp photo. Invoicing slips, the customer calls, and nobody can answer "where is my load?" without three phone calls. This proposal solves that with a **single authoritative order state machine**, enforced server-side, with every transition timestamped, attributed to a user, and immutable in an audit log. The Android app is a thin, offline-tolerant client against that state machine — not a second source of truth. That architectural decision alone eliminates 90% of the disputes that plague small logistics firms. --- ## 2. Architecture & Technical Plan ### Phase 1 — Domain Model & Backend Core (PHP / REST API) **Deliverable:** A versioned REST API with a hardened order lifecycle. - **Entities:** `Order` (LR number, consignment note), `Trip` (truck, driver, origin, destination), `Party` (consignor/consignee), `Invoice`, `POD` (proof-of-delivery attachment), `User`. - **State machine:** `BOOKED → DISPATCHED → IN_TRANSIT → DELIVERED → POD_RECEIVED → INVOICED → CLOSED`. Illegal transitions are rejected at the API layer, not the UI. - **Stack:** PHP 8.x, PDO with prepared statements (no string-concatenated SQL, ever), MySQL/PostgreSQL, JWT-based auth with short-lived access tokens + refresh tokens. - **Security:** bcrypt/Argon2 password hashing, role-based access control (Admin / Dispatcher / Driver), rate limiting on auth endpoints, HTTPS-only, input validation on every endpoint. - **Audit log:** Append-only `order_events` table — who changed what, when, from which device. ### Phase 2 — Android Application (Kotlin, native) **Deliverable:** A production-ready APK for your field users. - **Stack:** Kotlin, MVVM, Retrofit + OkHttp, Room for local caching, WorkManager for background sync. - **Offline-first:** Drivers frequently lose signal on highways. Status updates and POD photos are queued locally and synced when connectivity returns — with conflict resolution favoring the server's state machine. - **POD capture:** Camera integration, image compression before upload, GPS + timestamp stamping on delivery confirmation. - **UI:** Minimal, large-touch-target screens designed for one-handed use in a truck cab. Order list, order detail, status update, POD upload. Nothing else. - **Testing:** Unit tests on ViewModels and repository layer; instrumented tests on the sync queue. ### Phase 3 — Web Dashboard, Testing & Handover **Deliverable:** A lightweight web console for your three office users + full documentation. - **Dashboard:** Order creation, trip assignment, live status board, invoice generation, POD viewer, CSV export. - **Test coverage:** API integration tests covering every legal and illegal state transition; Android unit + instrumented tests; a manual QA checklist for the office workflow. - **Zero-regression discipline:** Every change ships behind a test. No feature is "done" until its test is green. - **Handover:** Source code in a private Git repo you own, `.env.example`, a one-page deployment guide, a 30-minute walkthrough call, and 30 days of post-delivery bug-fix support. --- ## 3.
