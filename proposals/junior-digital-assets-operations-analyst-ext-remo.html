2. Architecture & Technical Plan

Phase 1 — Isolation, Discovery & Reproduction (Day 1)

Objective: Establish a clean, isolated environment and reproduce the current operational reality before changing anything.

- Environment isolation: Dedicated Python 3.11 virtual environment (or Docker container) with pinned dependencies via `requirements.txt` / `pyproject.toml`. No global installs, no credential bleed. - Discovery inventory: Catalogue every data source referenced by Omega (exchange APIs, market-intelligence feeds, on-chain endpoints), documenting: - Auth model (key type, scopes, rotation policy) - Rate limits and backoff requirements - Response schema and known failure modes - Baseline reproduction: Script that pulls a fixed snapshot of each source and writes it to an immutable, timestamped artifact (`snapshots/YYYY-MM-DDTHH-MM-SSZ.json`). This becomes the ground truth for all later verification. - Deliverable: `discovery.md` + working baseline snapshot script.

Phase 2 — Implementation & Automated Verification (Day 2–3)

Objective: Build the operational pipeline and prove it works with automated tests.

- Ingestion layer: Modular fetchers with retry/backoff, explicit timeout handling, and freshness assertions (reject any payload older than a configurable threshold). - Normalization layer: Canonical schema for prices, volumes, and market-intelligence fields — so downstream consumers never parse raw vendor JSON. - Reconciliation: Cross-source comparison with tolerance bands; flags divergence beyond threshold rather than silently averaging. - Reporting: Deterministic report generator that reads only from a snapshot artifact — same input, same output, every time. - Automated verification: `pytest` suite covering: - Schema conformance - Freshness rejection (stale payload must fail) - Retry/backoff behavior on simulated 429/5xx - Reconciliation tolerance boundaries - Determinism of report output

Deliverable: Working pipeline + green test suite.

Phase 3 — Hardening, Performance & Handover (Day 3–4)

Objective: Make it safe to run unattended and hand it over cleanly.

- Credential hardening: `.env`-based secret loading, `.gitignore` enforcement, pre-commit hook that blocks accidental key commits, documented rotation procedure. - Performance: Batch requests where the API allows, cache immutable historical data, cap concurrent connections to respect rate limits. - Observability: Structured logging (JSON) with correlation IDs; a single `healthcheck` command that verifies every source is live and fresh. - Handover: Written runbook, architecture diagram, and a recorded walkthrough so any team member can operate the toolkit without you.

Deliverable: Hardened toolkit + runbook + walkthrough.

4. Regression Guardrails

Zero-regression is enforced structurally, not promised:

1. Snapshot-based testing. Every test runs against a frozen input artifact — results are reproducible and diffable. 2. Golden-file comparison. Report output is compared byte-for-byte against a committed golden file; any drift fails CI. 3. Contract tests on every source. If a vendor changes its schema, the test fails loudly *before* bad data reaches the desk. 4. Freshness gate. Stale data is rejected at ingestion, never propagated. 5. Pre-commit hooks. Lint, type-check, and secret-scan run before any commit lands. 6. Additive-only changes. New sources are added as new modules; existing behavior is never mutated in place. 7. Rollback path. Every phase is committed separately, so any phase can be reverted independently.
